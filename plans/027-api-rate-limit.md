## Outcome (2026-11-11)

Shipped as PR #809 (merged e4b76a7): binding, middleware and the six routes,
as planned. In production the limiter never refuses. A temporary log (PR
#810) showed `limit()` returning `success: true` for every request (45 of 45
from one IP at one location, CDG, past 30 per 60 s), with `namespace_id`
`1001` and again with a fresh `48271` (PR #811). The same code under
`wrangler dev`, with `cf-connecting-ip` set by hand, refuses the 31st
request. The log was removed again (PR #812).

Maintainer decision: leave it as is. The binding is harmless while it never
refuses and starts limiting if Cloudflare's side does. The API is therefore
not rate-limited in practice. A strict alternative, if it's ever needed, is
a Durable Object counter per client IP (no plan yet).

## Why this matters

The API has no accounts and no rate limit. Its expensive routes forward to a
compile service that builds one package at a time and answers 503 once its
queue is full, so a script calling them in a loop blocks compiles for every
user and keeps a container busy. CORS doesn't help: it only restricts
browsers. Plan 013 bounds what one request can carry; this plan bounds how
many requests one client can send, with Cloudflare's Workers Rate Limiting
binding, which needs no extra service.

## Steps

### Step 1: Confirm the binding's shape and the limits

Read Cloudflare's current documentation for the Workers Rate Limiting
binding (https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
and confirm, for the installed wrangler (4.158): the configuration key and
its fields, the allowed `period` values, and the runtime call. When this plan
was written, the expected shape was:

```jsonc
"ratelimits": [
  {
    "name": "COMPILE_RATE_LIMITER",
    "namespace_id": "1001",
    "simple": { "limit": 30, "period": 60 },
  },
],
```

and `const { success } = await env.COMPILE_RATE_LIMITER.limit({ key });`.
That shape is from memory, not verified against the docs: trust the docs.

Default limit to propose: **30 requests per 60 seconds per client IP**,
shared by all limited routes. Reasoning to give the operator: one person
editing compiles a few times a minute; importing the largest example is one
request; 30 leaves room for a classroom behind one address without letting a
loop monopolize a service that builds one package at a time.

**Verify**: you can quote the docs' configuration example and runtime call.
If they differ from the expected shape, use the docs' and note the
difference in your report.

### Step 2: Declare the binding

Add the binding to `wrangler.jsonc` twice: at the top level (local) and in
`env.production` (bindings aren't inherited). Put a comment above each, in
the file's style, saying what it limits and that the numbers are the
operator's to tune. Then `cd apps/api && pnpm cf-typegen`.

**Verify**: `grep -n "COMPILE_RATE_LIMITER" apps/api/cloudflare-env.d.ts` →
at least 1 match; `git diff --stat apps/api/cloudflare-env.d.ts` → a small
diff (the new binding). `pnpm typecheck` → exit 0.

### Step 3: The middleware, with a pure key function

`lib/rate-limit.ts`:

```ts
// Who a request is counted against: the client's address as Cloudflare
// reports it. Without it (local `wrangler dev`, the e2e runs), nothing is
// limited.
export const rateLimitKey = (headers: Headers) =>
  headers.get("cf-connecting-ip") ?? undefined;
```

and a Hono middleware `rateLimit` (`createMiddleware<AppEnv>`, as in
`db/middleware.ts`) that: computes the key; calls `next()` when there is no
key or no binding; otherwise calls the limiter and, when it refuses, answers

```ts
return c.text("Error: Too many requests. Try again in a minute.", 429, {
  "Retry-After": "60",
});
```

`lib/rate-limit.test.ts` (model: `lib/validation.test.ts`): `rateLimitKey`
returns the header's value, and `undefined` without it. Keep the middleware
itself out of the unit test if importing it pulls `hono/factory` types only
(it should load); if `node --test` can't load the file, split the key
function into its own module and say so.

**Verify**: `cd apps/api && pnpm test` → exit 0 with the new test;
`pnpm typecheck` → exit 0.

### Step 4: Attach it to the costly routes

Attach `rateLimit` per route, before the handler, on exactly: `POST /`,
`POST /import`, `POST /examples/:exampleId`, `PATCH /:id` in
`routes/scripts.ts`, and the two `POST` routes of `routes/verified.ts`.
Hono accepts middleware as an extra argument:
`.post("/import", rateLimit, async (c) => { … })`. Put it before the
handler so a refused request costs no database connection only if
`dbMiddleware` runs after it; `dbMiddleware` is attached with
`.use(dbMiddleware)` for the whole router, so a refused request still opens
a connection. Leave that as it is and note it.

**Verify**: `grep -c "rateLimit," apps/api/routes/scripts.ts` → `4`;
`grep -c "rateLimit," apps/api/routes/verified.ts` → `2`;
`cd apps/api && pnpm typecheck` → exit 0; `pnpm build` → exit 0.

### Step 5: Format and check

**Verify**: `cd apps/api && pnpm exec biome check --write wrangler.jsonc lib/rate-limit.ts lib/rate-limit.test.ts routes`
→ exit 0; `pnpm test` → exit 0; root `pnpm lint` → exit 0.

## Maintenance notes

- The limiter is per Cloudflare location and eventually consistent: it
  bounds abuse, it is not an exact quota.
- Production traffic reaches the API directly from browsers (CORS), so
  `cf-connecting-ip` is the visitor's address. If the API is ever put behind
  another proxy, the key must change or everyone shares one bucket.
- A user who hits the limit sees the 429 text in the app's error toast. If
  that happens to real users, raise `limit` in `wrangler.jsonc`: no code
  change.
- A refused request still opens a database connection (`dbMiddleware` runs
  first). Moving `dbMiddleware` behind validation and the limiter is a
  possible follow-up; it changes when the connection opens for every route.
