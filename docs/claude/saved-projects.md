# Saved projects and resumable tutorials

A saved project is the app state (`stateSerializer`) plus the client store as `exportStore()` dumps it, secret keys included (`apps/web/lib/utils/project.ts`, `hooks/use-projects.ts`). Two kinds (`ProjectKind`): leaving a tutorial saves it as a `tutorial` project and starting it again resumes it (`hooks/use-tutorials.ts`), its step shown from `State.tutorialProgress` without reading the snapshots; a sandbox or an example saved from the sidebar's Projects submenu is a `project` (`hooks/use-saved-projects.ts`, `components/lib/project-switcher.tsx`). Saving an example keeps its `exampleId` (the auto-deploy of its account), only the title changes.

- Snapshots go in their own IndexedDB database, `PlaygroundProjects`. Never put "miden" in its name, in any case: `clearMidenStorage()`, which runs before every store import, deletes every database whose name contains it.
- The database holds the `projects` store (the snapshots, megabytes each) and, since version 2, the `meta` store (`ProjectMeta`: kind, id, name, network, save time), written in the same transaction. The Projects submenu lists `meta` alone, most recently saved first, through a `["projects"]` query (TanStack Query) refreshed after each save and delete.
- The active project is `State.projectId` and `State.projectName` (persisted, so the app shell's title shows the name). Every state that starts a workspace has them empty, so New sandbox, Launch example and Start tutorial clear it. Save writes to the active project; Save as, and Save without one, ask for a name (`save-project-dialog.tsx`) and create one. That dialog and the delete confirmation (`delete-project-alert-dialog.tsx`) open through `State.saveProjectDialogOpen` / `deleteProjectDialogOpen` and render in `AppSidebar`, outside the switcher: on a phone the switcher is in the sidebar sheet, which unmounts it when it closes (and it closes so the dialog shows over the page). `AlertDialogAction` is a plain button, so the delete dialog closes itself before deleting. The Projects submenu shows in tutorials too, as the list alone: a tutorial can open a project, but only sandboxes and examples save or delete one. Leaving a project (opening another, a new sandbox, an example, a tutorial) doesn't save it. Clicking the active project in the list only goes to its accounts page: reloading its last save would lose what changed since. Delete removes the active project and leaves the workspace open, unsaved. No rename yet. The Save dialog refuses a blank name and one the list already has (ignoring case and surrounding spaces): duplicates can't be told apart in the menu, and Save as never overwrites.
- Opening a project: `leaveTutorial()` (exports the current store), then `switchNetwork(project.networkId)`, then `pushState` with the record's id and name, the **live** `completedTutorials` and `tutorialProgress`, `nextStore` and a `fallbackState`: a fresh sandbox on the project's network (`freshSandboxState`). The order matters: `switchNetwork` re-initializes the client and unmounts the page (`MidenClientGate` shows the app shell until the new client is ready), `popState` then imports `nextStore` into the new network's store on remount. By the time an import fails, the previous store is cleared, so the fallback can't be the previous workspace.
- Nothing cancels what's running when a workspace is replaced (a sync, a deploy, a transaction). `POP_STATE` bumps `State.workspaceRun`, the `dispatch` from `useGlobalContext` is bound to the run of its render, and the reducer drops an action from an earlier run, so old work can't write to the next workspace. `globalDispatch` (context only) is the unbound, stable one. `NetworkBadge` starts no sync or example deploy while `nextState` is queued. A deploy abandoned this way loses its account with the store, and reports nothing; a project saved mid-deploy deploys a new one when opened.
- During a switch (`nextState` queued) the store is being cleared and imported, so Save, Save as and Delete project are disabled, and `saveProject` refuses a workspace that's being or was replaced, before and after its export (`workspaceLeft` in `lib/utils/workspace-guard.ts`, whose live values `GlobalContextProvider` writes because it stays mounted through a network switch). `leaveTutorial` doesn't export then either: the queued state has the progress.
- A second switch during an import stays queued: `POP_STATE` names the state it `imported`, applies that one, and keeps a newer `nextState`, whose store `popState` imports next.
- Every import outcome clears the state it was queued with, or the app would wait on it forever with syncing stopped. A failed import falls back to `fallbackState`, or a new sandbox on the network when there is none (a new sandbox, an example, a tutorial started fresh), with an error toast; if that import fails too, the toast asks for a reload. `e2e/workspace-switch.spec.ts` covers these by holding the switch inside `clearMidenStorage`, since timing can't hit a window of milliseconds.
- Snapshots carry the client version that wrote them. An SDK bump migrates them on import, but a rollback makes the SDK refuse them. `popState` then starts over from `fallbackState`: the tutorial from its start, a project as a new sandbox, each with its own warning toast.
- Every persisted state and snapshot holds a copy of each built-in script and component (`lib/types/default-scripts`, `default-components`). `withDefaultScripts` refreshes the copies of the built-ins the code still has, and leaves the others alone. So a removed built-in's copy would turn into one of the user's scripts: listed on the Scripts page, and found by the tutorial steps that look for the script the user created (`!defaultScriptIds.includes(id)`). When removing one, add its id to `retiredScriptIds` / `retiredComponentIds` next to the lists, as for the MASM counter (`counter-contract`).
- A network reset (testnet, or Partner Mainnet before public mainnet) invalidates them: `isRestorable` compares their genesis header with `genesisBlockHeader` in `lib/utils/store.ts`, so update that header with the reset. `loadProject` deletes a snapshot it can't restore; opening one reports it as an error.

`spec/project-export.md` explores taking a project out of the playground to continue it with the `miden-client` CLI (account and note files, not the store dump): explored, not scheduled.
