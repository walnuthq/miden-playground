# Upgrading the Miden packages

When bumping `@miden-sdk/*`, also update `CLIENT_VERSION` in `apps/web/lib/utils/store.ts` to the new version. It stamps the stores the tutorials seed from `defaultStore`, and the SDK refuses to import a store stamped by a client newer than the running one. Bump the `@miden-sdk/*` pins in `pnpm-workspace.yaml` `overrides` too (`apps/web/lib/utils/sdk-version.test.ts` fails when the three disagree). Then regenerate the examples' compiled snapshots (see `examples.md`), and check that the script templates still compile and that the package embedded for tutorial 8 is up to date (`pnpm templates:check`, then `pnpm templates:sync` if it says so, see `script-templates.md`). Then set `MIDEN_ASSEMBLY_VERSION` in `apps/web/scripts/sync-masm-vocabulary.ts` to the `miden-assembly` api-compile's `miden-assemble` pins, and run `pnpm masm:sync` in `apps/web` (see `masm-highlighting.md`). If the new version is younger than pnpm's minimum release age, exempt exactly that version of each package in `minimumReleaseAgeExclude`, and remove the entries once it ages out.

- Restart any running dev server after the install. Vite keeps serving the SDK it pre-bundled at startup, so the new `CLIENT_VERSION` meets the old client and every seeded store is refused ("exported by a newer client"): tutorials never start.
- The release notes list API changes only. Compare the crate versions too (`miden-client`, `miden-protocol` in the web-sdk `Cargo.toml` at both tags): a protocol bump leaves `apps/api/templates/project-template` and api-compile a version behind, so check that an example still deploys and a tutorial still runs on testnet before merging.
- Diff the skills the packages ship (`node_modules/.pnpm/@miden-sdk+miden-sdk@<old>` against `@<new>`, `skills/` and `AGENTS.md`): they document behaviour changes the notes leave out.
- Bread Wallet has to be on the same SDK minor as the playground. For a Guardian account it rebuilds a custom request (`requestTransaction` with a `CustomTransaction`: the Create Note dialog, tutorials 8, 9 and 11, the bank example) and compares it with ours byte for byte, in its own SDK's layout: 1.17.11 (SDK 0.17) refuses a request serialized by 0.18 ("Custom requests without authentication currently support only own output notes", in the extension's console only; the page just never sees the note), and 1.18.0 (SDK 0.18) accepts it but refuses a 0.17 request the same way (the page gets `NOT_GRANTED`). The extension updates itself from the store, so users are on the new Bread before we are: bump the SDK soon after a Bread release that moves to a new SDK minor. Check `@miden-sdk/miden-sdk` in 0xMiden/wallet's `package.json` at the latest release tag, and bump `.bread-wallet/version` (`pnpm bread-wallet latest`) with the SDK.
- A Bread release can redesign its pages: the e2e fixture (`apps/web/e2e/bread.ts`) reads Bread's home page to know the wallet is unlocked and funded (1.18.0 renamed "Total balance" and turned the assets list into plain text), and tutorials 3 and 4 read its confirm page (1.18.1 replaced the "Amount" row with one amount per party: "· you" and "Recipient"). When every Bread spec fails within the fixture after a bump, look there first.
- `@openzeppelin/miden-multisig-client` follows the Guardian server's version, not the SDK's (0.19.1 for SDK 0.18, with `guardian.openzeppelin.com/status` naming the server's). Bump it with the SDK and read the Guardian release's rollout notes: a server ahead of the client refuses its sessions.
- Tutorial 5 is marked `unavailable` in `components/tutorials/meta.ts` and its e2e spec is `test.fixme`: since 1.17.12 Bread signs a dApp's `signBytes` word under a domain tag (0xMiden/wallet#2161), and the multisig client's `MidenWalletSigner` (0.19.1) still expects the raw word signed, so a guardian wallet can't be deployed, loaded or signed for with Bread ("the ECDSA public key does not match the signer commitment"). Sandbox Guardian accounts fail the same way. Reported as OpenZeppelin/guardian#611: on each multisig client bump, remove the `test.fixme`, run the spec, and drop `unavailable` if it passes.
