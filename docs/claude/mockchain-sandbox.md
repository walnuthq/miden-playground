# MockChain sandbox (`mmck`)

A sandbox whose chain runs in the browser: the app's client is a mock client (`MockWasmWebClient`), so nothing reaches a node, a prover or a faucet. `spec/mockchain-sandbox.md` has the spike's findings and the plan (PRs A to F). PRs A to E are in, so it's on: the home page's third sandbox card and the switcher's "New MockChain sandbox" start one, in every build. PR F (tutorials 1 and 2 on it) is optional and undecided: no tutorial runs there.

- The React SDK's `MidenProvider` takes no client: it calls `WasmWebClient.createClient(rpcUrl, …)`. `lib/miden-client.ts` replaces that static with `mockAwareCreateClient` (`lib/mock-chain.ts`), which returns a mock client for the sentinel `networks.mmck` (`"mock"`, which the SDK's `resolveRpcUrl` passes through) and calls the SDK's for every other URL. An SDK bump that changes how the provider creates its client breaks this silently: `mmck` would try to reach a node at "mock".
- `lib/mock-chain.ts` imports nothing from the SDK at run time (types only), so its unit tests run on plain node with fakes. Keep it that way: the SDK doesn't load there.
- `provers.mmck` is unset. With `"local"` the React SDK hands the mock client a local prover and it generates a real proof (over 30 s for a wallet); without one it uses its own, which doesn't prove.
- The chain lives in the client's memory, not in its store, and `exportStore()` leaves it out. It's saved to the IndexedDB database `PlaygroundMockChain` (no "miden" in the name, as for `PlaygroundProjects`) when it's created, replaced, and after a block (`proveMockBlock`: nothing else produces blocks, and no caller uses it yet). The factory gives it back to the client on load. A store ahead of its chain hangs initialization with no error, so whatever changes one must change the other.
- The store's name is the SDK's default, `mock_client_db` (since 0.18.1 a mock client takes a `storeName`, which neither of the app's mock clients passes yet: giving the Simulate tab's client its own store would lift the limits below), the one the Simulate tab's client deletes and uses on the other networks (`simulation.md`). Two mock chains never share a genesis, so two clients can't share the store.
- So the Simulate tab has no simulated account on `mmck` (`hasSimulatedAccounts`, `lib/simulation/can-simulate.ts`): an account component's tab says to deploy it and invoke it from the account page (free and under a second here, and the Invoke dialog previews), and a note or transaction script runs on the sandbox's accounts only, executed on the app's client, which writes nothing. `simulationClient()` refuses on its own while the tab's client is the sandbox's (`tabRunsMockChain`), whatever the UI offers. Running them on the sandbox's client instead was the other option of the spec: every storage edit would leave an account in the user's store and saved projects, and every staged foreign account a block on their chain.
- `defaultStore("mmck")` seeds no genesis header and no protocol config: each mock chain has its own. After a store import, `popState` replaces the live client's chain (`replaceMockChain`): with the one saved with the store (`State.nextMockChain`, a saved project's), or with a new one (null), which writes its genesis to the store. `replaceMockChain` calls `createMockClient` on the wasm client under the wrapper, an internal the SDK's worker calls the same way on each sync; it's needed because a new sandbox on the same network doesn't re-create the client.
- A saved project on `mmck` carries its chain (`Project.mockChain`, dumped after the store is exported: a store behind its chain syncs, a store ahead of it never does). `isRestorable` refuses a `mmck` snapshot without one. A chain the client can't read (another SDK version) fails the import like a refused store, and `popState` falls back to a new sandbox.
- One tab at a time: every tab shares `mock_client_db`, and each would run its own chain over it. The factory takes a Web Lock (`mockChainTabLock`) before it creates a mock client and frees it when the app's client is a real network's again; the browser frees it with the tab. It's one hold for the tab, shared by the clients created in a row (StrictMode, a restart). A tab that can't get it shows "the MockChain sandbox is open in another tab" with Retry (a reload), and no reset: the data is the other tab's. A tab on another network isn't held back. Its Simulate tab's mock client holds the same lock, shared (`simulationStoreLock`): several tabs simulate at once, none while a tab runs the sandbox (the run fails with a message naming the other tab), and a sandbox that starts takes the lock from them (`steal`, after `locks.query()` shows only shared holders), in its own tab too, which stops their clients. A sandbox never takes it from another sandbox. Not covered: a sandbox no tab has open (its tab was closed on `mmck`) while a tab that was already on another network simulates. The store is emptied under the saved chain, and the next load on `mmck` fails its syncs until a new sandbox or a project is opened. Two tabs on different networks also share the persisted app state (one `localStorage` key, last writer wins), on every network.
- A fresh `mmck` state has no USDCx Faucet entry: the chain has no public faucet.
- The mock RPC panics on an account its chain doesn't hold (`mock.rs:748` in miden-client 0.17.5), and the client is dead from then on: a call in the worker is rejected with `WebClient worker failed: …`, as is every call after it (since SDK 0.18.1; before, they never settled) (a panic on the page's thread wasn't rechecked on 0.18.1). The panic is in the client's worker for a call that runs there, and on the page's thread for the others (`importAccountById`: the page gets an uncaught `RuntimeError: unreachable`). The factory watches both for the client it returned, until the next client is created. On a crash it terminates the client and `MidenProvider` (`components/providers/miden-provider.tsx`) builds a new config, which makes the SDK's provider create a client on the saved chain, with a toast. A restart that crashes within `STARTUP_CRASH_MS` isn't restarted again (the store, the chain or the app state is what crashes it): the "Failed to initialize" screen shows, whose "Reset local data" also deletes the saved chain. So does an outdated `mock_client_db` deleted on load (`deleteOutdatedMidenStores`). Any uncaught WASM trap on the page counts while `mmck` is the network, whichever module raised it.
- Nothing produces blocks on the mock chain. Every submit proves one: `submitNewTransaction` (`hooks/use-transactions.ts`) and the account commit below call `proveMockBlock`, then `sync()`. `useTransaction` syncs too, but before the block exists. A new path that submits a transaction must do the same, or it stays pending.
- No funding: the mock chain charges no fee and has no faucet API. On `mmck`, `fundAccount` (`hooks/use-fund-account.ts`) submits an empty transaction, which puts the new account on chain (nonce 1), so whatever expects a committed account works.
- The app's sync loop (`network-badge.tsx`) runs on `mmck` as elsewhere: it's what lists notes. `clientGetAllInputNotes` skips its stateless `RpcClient` there (it can't reach a chain that lives in the client), so the notes keep their records' metadata. `clientGetLatestBlockNum` and `clientGetNotesById` still build one for `localhost`: don't call them on `mmck` (tutorial 3's mint button does, and tutorials don't run there).
- Nothing is sent for verification on `mmck`, neither a deployed account's packages nor a custom note's script (the registry has no MockChain, the API answers 400). The account page's "Verify account component" prompt and the note page's "Verify note script" button are hidden there.
- Import account is hidden on `mmck`: an id the chain doesn't hold is the crash above. A restarted client transacts: checked on 2026-11-19 by a page-thread panic from Import account (then visible), followed by a wallet created and committed in the same page. A crash in the worker wasn't reproduced.
- A new `mmck` sandbox starts with the counter example's packages (`sandboxStarter`, `counterExampleStarter`), as a Mainnet one does: it needs `apps/api`.
- Addresses read `mmck1…`. The React SDK's `normalizeAccountId` picks the prefix from the RPC URL's text and falls back to testnet's, so a MockChain account would read `mtst1…` on its page and in its URL while `formatAddress` printed `mmck…` in the tables. `accountAddress` (`lib/web-client.ts`) is what the app calls instead: the SDK's function on a real network, `NetworkId.custom("mmck")` while the tab's client is the sandbox's (`tabRunsMockChain`). Use it for any address the app shows or stores. The SDK parses an address of any prefix, so its hooks take these.
- No wallet, so nothing that needs one: the header's wallet button, the Guardian entries of "Create new account" and the deploy dialog's Network Account auth component (no network transaction builder runs on a mock chain, so its notes would never be consumed) are hidden.
- The home grid keeps two columns, so the third card sits alone on its row. `e2e/mobile/mobile-sandbox.spec.ts` starts a sandbox from it on a phone.
- `e2e/mockchain-sandbox.spec.ts` runs against production too. Its helper waits for the badge to read `MockChain | #N` before it touches the page: the counter packages take longer to arrive there, and until the switch is over the accounts page is still the previous network's.
- To try it by hand, pick "New MockChain sandbox" in the switcher, with `apps/api` running for the counter packages.
