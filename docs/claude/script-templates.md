# Script templates

The "Create script" dialog creates scripts from `apps/api/templates/*.masm` (`lib/templates.ts`): each type with no example, and each example of the web app's `scriptExamples` (`apps/web/lib/types/script.ts`). Every one must compile. `pnpm templates:check` in `apps/api` creates and compiles each through the local API (`pnpm dev`, with api-compile running), then deletes them. Run it after editing a template or its schema, and after bumping the SDK or the api-compile image: SDK API changes break templates silently.

- The counter note and counter script examples `use counter_account` but come without it: tutorial 11 teaches adding the user's own `counter-account` script as a dependency. The check does the same (`userDependencies`), so keep it in sync when an example gains such a dependency. `count-reader` comes with the `counter-account` template as a built-in dependency (`lib/default-dependencies.ts`, whose commitments are the templates' as api-compile builds them under those names: re-read them after editing `counter-account.masm` or `basic-wallet.masm`, or bumping api-compile).
- The check also compiles the code the tutorials add to a template (`tutorialEdits`, from `apps/web/lib/utils/tutorial-code.ts`). An edit whose anchor is gone from the template fails it too. Today: tutorials 7, 8 and 12. `keepsSchema` fails the check when the edited package loses the template's schema (the next steps use the typed forms), `losesNoteSchema` when an edited note keeps it (the next steps give raw storage values). Add a tutorial's edits there when it gains a snippet.
- Tutorial steps cite the templates' line numbers: re-count them after editing a template. A step with several snippets cites a line only while no earlier snippet has moved it, and names the place otherwise.
- The templates are written to be quoted line by line: a comment per stack effect (`# => [...]`), a `#!` doc comment per procedure with its `Inputs:` and `Outputs:`. A re-export (`pub use`) can't take a `#!` doc comment (the assembler warns), which is one reason `basic-wallet` writes the standard procedures out instead of re-exporting them; the other is that api-compile reads parameter names from the source, and a re-export has none.

## Standard procedures and the wallets that run them

A procedure is known by its MAST root, a hash of its code. `basic-wallet.masm` and `auth-no-auth.masm` are the standard components (miden-standards' `wallets::basic` and `auth/no_auth`) instruction for instruction, so they have the standard roots: checked on 2026-11-26, the wallet's three roots are the ones a `pub use` of the standard procedures gives, and an account with the template's no-auth has the code commitment of one built with the SDK's `withNoAuthComponent()`. Keep them identical, or a standard wallet's notes stop working on them and the SDK stops recognising the auth component.

`p2id-note.masm` reaches the account through `miden::standards::wallets::basic::move_note_assets_to_account`, which `call`s the standard `receive_asset`: any wallet consumes it, the SDK's, Bread's, Para's, and an account built from the `basic-wallet` template. It has no script dependency. Its storage is the target's id, prefix then suffix (the web app's `account-id` field layout), not the standard P2ID's four items (target, then a two-felt salt), so its root isn't the standard P2ID note's: a wallet that only recognises standard notes by their root sees it as a custom note.

## Hand-written schemas

A MASM package carries no storage schema (decision 3 of `spec/remove-rust.md`), so a template whose storage or note inputs the web app's forms should type ships one next to it: `templates/<name>.schema.ts`, in the shape of `metadata.storage` and `metadata.noteStorage`, listed in `lib/template-schemas.ts`. Today: `counter-account` and `count-reader` (`storage`), `p2id-note` (`noteStorage`). The blank templates, `basic-wallet`, `auth-no-auth` and the counter's note and script have none.

- The API sets `metadata` from the schema when it creates a package from a template (`templateMetadata`); fork and project links copy it with the package. Import, and anything forked from a schemaless script, has none.
- `compiledMetadata` (`lib/package-metadata.ts`) decides `metadata` on each compile that builds, and drops a schema that no longer describes the source. Nothing brings a dropped schema back. A compile that fails keeps the schemas as they are (`failedBuildMetadata`): its source may be a typo away from the template's, and an unclosed string makes its slot names unreadable.
  - `storage` holds while the slot names the source declares, its `const NAME = word("…")` constants, are the schema's, as a set (`lib/storage-slot-names.ts`). The reader follows the assembler's lexer (`#` comments, `"…"` strings with `\` escapes) and answers "can't tell" for a `word(…)` that isn't alone on the right of a `const`, or a name with an escape: the schema is dropped then. Only names are compared: a slot whose use changes under the same name keeps its type.
  - `noteStorage` holds while the source is byte for byte the template's as shipped: a note's inputs have no names in MASM. `metadata.template` names that template while the schema holds. A comment-only edit drops it too, and undoing the edit doesn't bring it back.
- An account component left without a `storage` schema gets `metadata.slotNames`, the names its source declares, on each build: the forms start from them (`docs/claude/simulation.md`). So an import of an exported template gets its slots' names back, not their types or descriptions.
- `pnpm templates:check` fails when a template's declared slot names aren't its schema's, and when a package created from it loses its schema on its first compile.
