# Simulations (the script page's Simulate tab)

The console of an editable script has two tabs: Output (the log) and Simulate, which runs the compiled package locally and shows what it would change. Nothing is proven, submitted or saved. A read-only script has the console too when it holds a package (`canSimulate`, `spec/simulate-read-only-scripts.md`): the tutorials' embedded packages (`count-reader`, `counter-account`, the Rust `basic-wallet`) and the counter example's packages tutorial 9 starts read-only. It opens on Simulate; nothing else changes for the script, and "Apply to state" writes to the tab's in-memory slots and vault only. The built-ins assembled from MASM have no package and no console: `basic-wallet` is already on every simulated account (adding it again fails on duplicate procedures), `fungible-faucet` needs a faucet account, authentication components aren't called directly, and the built-in notes' storage is raw felts that can't name the simulated account. On a read-only script, the sentences about an unresolved dependency and `simulationBlockedReason`'s reasons stop at the cause: there's no compile to ask for. Item 11 of `spec/editor-console-improvements.md` has the plan and the SDK spike's findings.

- Account components, and note and transaction scripts on the simulated account, run on a throwaway account (basic wallet, No Auth, the components) in a mock client (`lib/simulation/simulation-client.ts`, `MockWasmWebClient`), not the app's client: the SDK can't delete an account and an account's id changes with its storage, so every storage edit would leave an account in the user's store and saved projects. Every mock client opens the IndexedDB store `mock_client_db`; it is deleted when the client is created, once per page load, on the first run.
- Don't run a simulation on the app's client through anything that writes to its store (`newAccount`, `submitNewTransaction`, importing a note). `executeTransaction` and `executeProgram` write nothing, on either client.
- Every run starts from the storage slots and the vault shown: at nonce 0, or 1 when the vault holds assets. "Apply to state" in the result dialog copies the resulting values into the slots and the resulting balances into the vault's rows (`applyVaultChanges`); nothing else carries state from one run to the next. The account is built on the first run after a compile, a slot edit or a vault edit (`useSimulation`, cached per client by commitment, slots and vault).
- The vault (`spec/simulate-assets.md`): rows of a simulated asset and an amount (`components/procedures/vault-editor.tsx`), empty by default, so a script that needs no asset gets no seed. `AccountBuilder` can't build an account with assets, so `seedVault` (`lib/simulation/run.ts`) has the new account consume a P2ID note carrying them (the standard basic wallet takes it) and applies that transaction to the mock client's store only, at `getSyncHeight()`: never proven, submitted or put in a block. The mock chain can't hold it: the note was never created on the chain, and `proveBlock` panics on it, then on every later block (a foreign staging's) if it was submitted. Applied to the store alone, every later transaction and program on the account sees the assets, and the chain never learns of it. About 80 ms the first time, 20 ms after. The id doesn't change (it depends on the storage, not the vault). `createSimulatedAccount` returns the state after the seed (`client.getAccount`): the baseline, so the seed never shows as a change. A staged foreign account has no vault: it must be committed, which a store-only seed can't be (minting the note from the faucet in the same block works, 170 ms and a block; no example needs it yet).
- Simulated assets (`lib/simulation/simulated-assets.ts`): a list of symbols per script (`SIM` by default, more through "New asset": 1 to 12 uppercase letters, the faucet's `TokenSymbol`), in memory like the slots (`useSimulatedAssetSymbols`), and one faucet per client and symbol (`mockFaucet(client, symbol)`, about 300 ms, uncommitted, no decimals). The form holds stand-ins (`simulated:asset:<symbol>`, which `simulatedAccountName` refuses: a package name has no colon) wherever a simulation takes an asset or a faucet: the vault's rows, a note's assets, an `Asset` argument (the dropdown's "Simulated" group), an `AccountId` argument or a typed note storage field (as "<symbol> faucet"). The hooks make the faucets the run uses (`mockFaucetIds`), resolve the stand-ins before encoding (`resolveSimulatedAsset`), and return `faucetLabels` for the result dialog and `vaultChanges` (final balances by stand-in) for "Apply to state". A sandbox account takes none: its run refuses them, and switching to one clears the note's assets.
- An `Asset` argument's id is the faucet's prefix and its suffix plus `0x11` (composition fungible, version 1, as `FungibleAsset.vaultKey()` gives it): another value is an id no vault holds, and a balance read gives zero.
- The slots are in memory, per script (`lib/simulation/simulation-state.ts`), like the console's log: not in `State`, not saved with projects.
- A package's schemas come from api-compile (`storage` and `noteStorage` next to the manifest, `miden-package-metadata/src/schemas.rs` in miden-source-code-verification), stored in the API's `metadata` column and returned as `Script.metadata`. It is null or missing for drafts, failed builds, built-ins, scripts persisted or saved before it existed, and any build by an api-compile older than the schemas: every use falls back.
- With a storage schema the tab lists exactly its slots, at their defaults (`0`, the schema's default word, an empty map) with their descriptions, and offers no slot to add or remove. A recompile keeps the edits of the slots it still has and drops the others (`mergeStorageSlots`, `lib/utils/storage-schema.ts`). Without one the slots start from a workspace component made from the script, else empty, and are added by hand.
- With a note storage schema, a note's storage is one typed field per schema field (`lib/utils/note-storage.ts`), flattened in declaration order as the compiler's `ToFeltRepr` writes them: an account id as its prefix then its suffix (unlike a procedure call's `push.<suffix>.<prefix>`), a word as its four elements, a `u64` as its low then high 32 bits. Verified with the P2ID template: the note is consumed when its field names the target, and its assertion fails otherwise. A field the form can't type (a record the note defines, an option, a variant) turns the whole note back to raw felts, with the schema's fields listed as a hint.
- A run's changes are shown against the simulated account's real initial state (`createSimulatedAccount` returns it), not against the slots: a new account's first transaction reports every slot as created, its other components' included (the storage schema commitment).
- A slot value, a map key or a map value is a felt (a word's first element) or a whole word in hex: `lib/utils/storage-slots.ts`, which `wasmStorageSlotFromStorageSlot` uses for deployed accounts too.
- A state-changing procedure runs twice: as a transaction for its effects, and as a program for its return value, which a transaction doesn't give.
- The raw client's `executeProgram` returns a `FeltArray` (`length()`, `get(i).asInt()`). The React SDK's `useExecuteProgram` converts it; `lib/simulation/run.ts` reads it directly.
- Note and transaction scripts run against a target picked in the tab (`useTargetSimulation`, `simulateNote`, `simulateTransactionScript`): a note made from the script, never submitted, is the transaction's unauthenticated input (`withInputNotes` with a `NoteAndArgs`), and a transaction script takes its `Word` argument with `withScriptArg`. A sandbox account runs on the app's client, and the result dialog shows the changes against the account in app state, with no "Apply to state".
- The target dropdown's "Simulated account" (`spec/simulate-throwaway-target.md`) runs on the mock client instead: a throwaway account (`createSimulatedAccount`) with the standard basic wallet, No Auth, and one component per `account-component` dependency of the script that resolves (`foreignDependencies`, the same resolution as foreign accounts; none gives a bare No Auth wallet). The standard and the Rust basic wallets coexist on it. It's never committed: an account at nonce 0 the chain never saw runs a transaction script or consumes an unauthenticated note all the same. Its storage is edited under the form, one editor per dependency, in `useDependencyAccounts`'s slots (`${scriptId}:foreign:${dependencyName}`: a script is either an account component or a note or transaction script, so the keys never clash), and "Apply to state" applies the result to each dependency's slots and to the vault. It has one vault, whatever its dependencies, edited above their storage and keyed by the script's id like an account component's (a script is one kind or the other). It's cached per client by each component's commitment and slots and by the vault, like an account component's. Its id changes with every edit, so the form holds stand-ins (`SIMULATED_TARGET`, `lib/simulation/simulated-target.ts`, and the simulated assets' stand-ins), resolved during the run: a typed account field of the note's storage can name it, raw felts can't. A dependency is always the target's, never a foreign account: a note or transaction script that makes a foreign call isn't served on it. When the script's `accountProcedures` name a root none of its components has, the intro names them (`simulatedTargetMissing`), but the account stays offered: P2ID runs without `receive-asset` when it carries no asset. Switching between it and a sandbox account clears the note's assets and any account field naming it or a simulated asset's faucet.
- A note's asset makes the client load its faucet as a foreign account: from the client's own store first, then from the RPC (`fetch_public_account_inputs`, miden-client 0.17.5 `src/transaction/mod.rs`), which on the mock client panics on an id its chain doesn't hold. So on the simulated account a note carries only simulated assets (above), never a sandbox faucet's: the form takes amounts in base units, and the result dialog shows the same numbers. A reset client makes new faucets. The result dialog names them through `faucetLabels` ("Simulated asset" and the symbol): they aren't in app state. A note carries a list of assets (`clientCreateNoteFromScript`'s `assets`), the same rows as the vault.
- A note whose script doesn't take the asset it carries fails the kernel's last check, on either client: the assets of the account and the notes must add up to the same total before and after (`ERR_EPILOGUE_TOTAL_NUMBER_OF_ASSETS_MUST_STAY_THE_SAME`, miden-protocol 0.17.1 `asm/kernels/transaction-core/src/epilogue.masm`). The executor reports only its code, 4544980346559459778: the first felt of the Blake3 hash of the assertion's message (`error_code_from_msg`, miden-core). `targetErrorHint` (`lib/simulation/run.ts`) matches that code and adds the explanation to the log, as it does for a missing key, and for code 644413868907058392 (`ERR_VAULT_FUNGIBLE_ASSET_AMOUNT_LESS_THAN_AMOUNT_TO_WITHDRAW`: more removed than the vault holds), on every run, a procedure's included. To name a new code, hash the `ERR_*` messages of `~/.cargo/registry/src/*/miden-protocol-<v>/asm` and `miden-standards-<v>/asm` with Blake3 (`@noble/hashes`) and take the first 8 bytes, little-endian, modulo the field's prime. The counter example's increment note is such a note. After an SDK bump, `script-simulate.spec.ts` fails on the hint if the message, and so the code, changed.
- The target dropdown lists only the sandbox accounts whose code has every root in `metadata.accountProcedures` (`useScriptTargetAccounts`), and always offers the simulated account above them, preselected once the filter has settled when no sandbox account qualifies. The roots are the account procedures the script `call`s, from api-compile's MAST walk. The checks use `AccountCode.hasProcedure` on the store's account, read only, queued with the simulations. They're cached by code commitment. An account that can't be read is kept. Only the target dropdown is filtered: the note storage's account fields and the Asset dropdown list every account. An absent field or `null` means no filter, and `[]` means every account. Procedures are named from the workspace's scripts, the built-ins and the embedded Rust basic wallet. The P2ID template calls that wallet's `receive-asset`, which no deployed account has unless it was built with that component (tutorial 8's Test Wallet).
- An account whose key isn't in the local keystore can't be simulated: `executeTransaction` and `executeForSummary` both fail on the `miden::protocol::auth::request` event. The log then says to pick a No Auth account or a wallet created here.
- `components/procedures` (the arguments form, the procedures list, the storage slots editor) and `lib/utils/procedure-inputs.ts` know nothing about what runs a procedure: they take handlers. The account page's Invoke dialog (`components/account/invoke-procedure-arguments-dialog.tsx`) uses the same form and encoding, and `decodeProcedureResult` for a read-only call's result.
- A procedure that calls another account's procedure (FPI) runs against a foreign account staged on the mock chain (`spec/simulate-foreign-calls.md`). The mock client's RPC serves only the accounts committed on its chain, and its lazy fetch finds them without a declaration, as on a real network. One account is staged per `account-component` dependency of the script whose package resolves (`foreignDependencies`, `lib/simulation/foreign-accounts.ts`), in this order: a workspace script with the same id, `masp` and `commitment`; any workspace script with that `commitment` and a `masp` (the Count Reader example's `counter-account` carries the API's built-in id; the embedded `count-reader` of tutorial 10 depends on the embedded counter, `lib/tutorials/count-reader.ts`, whose commitment `count-reader.test.ts` checks against the package's manifest, so it resolves to the workspace's `counter-account` there); a package the web app embeds (`lib/simulation/embedded-packages.ts`, loaded with a dynamic `import()`: the embedded counter has the built-in dependency's commitment). A dependency's `commitment` is its package as the script was compiled against it: a workspace script with the same id and another commitment was recompiled since, its procedure roots aren't those the script calls, and it doesn't resolve ("stale": the tab asks to recompile the script). A staged account is a simulated account (`createSimulatedAccount`) made from the dependency's package and the slots of the tab's "Foreign accounts" block (keyed `${scriptId}:foreign:${dependencyName}` in `simulation-state.ts`, starting slots as for the script's own), then committed by `stageForeignAccount` (`lib/simulation/run.ts`): an empty transaction (No Auth bumps a new account's nonce), `proveTransaction` (a dummy proof on the mock client), `submitProvenTransaction`, `applyTransaction`, `proveBlock()`, `syncState()`. About 100 ms the first time, 40 ms after. Staging happens at Invoke, before the caller's account, never on a slot edit, and not for a procedure whose `callsForeign` is `false` unless an argument names a staged account: each staging adds an account and a block. It's cached per client by commitment and slots, like the caller. An `AccountId` argument picks a staged account in the dropdown's "Simulated" group (`SelectAccountDropdownMenu`'s `simulatedAccounts`): its id changes with every slot edit, so the form holds a stand-in (`simulated:<dependency name>`) that `useSimulation` replaces with the staged id before encoding. Several foreign accounts coexist, and an older one stays usable after an edit stages a new one. Only one level: a staged account's own dependencies aren't staged.
- The mock RPC keeps a snapshot of the chain per block, so runs slow down as stagings pile up: about 370 ms a run (staging and caller included) after the first, 520 ms after 50 (measured 2026-11-16). After `STAGINGS_PER_CLIENT` (100) stagings, `withSimulationClient` discards the client once the run is over, and the next run starts a new one.
- A sandbox account is still out of the mock chain's reach: picked as a foreign call's account, it makes the mock RPC panic (`committed_account(account_id).unwrap()`, miden-client 0.17.5 `test_utils/mock.rs:748`). The panic happens inside the client's worker, and the SDK never settles the call: left alone, the row stays on "Invoking…" and every later simulation waits behind it in `enqueueSimulation`'s queue (account components, notes, transaction scripts and the target filter alike) until a reload. So every mock-client run goes through `withSimulationClient` (`lib/simulation/simulation-client.ts`): the worker's `error` event (caught about a second after the panic; `client.worker` isn't in the SDK's typings) or a 60 s timeout discards the client and calls `terminate()`, which rejects the hung call ("WebClient terminated"), and the run fails with a message saying the client was reset. The next run creates a new client, whose store starts empty: `useSimulation` caches simulated and staged accounts per client, so they're built again. So the tab doesn't offer one where it knows better: for an export whose `callsForeign` is `true`, every `AccountId` argument lists the sandbox's accounts disabled, with the reason as a line in the menu (`sandboxAccountsDisabledReason`, `lib/simulation/blocked.ts`, passed to `ProceduresList` as `sandboxDisabledReason` and down to `SelectAccountDropdownMenu`), and only the "Simulated" group can be picked. A sandbox account picked before the rule applied (a recompile that brought the flag) is cleared (`withAccountIdsAmong`, `lib/utils/procedure-inputs.ts`). All the `AccountId` arguments of such a procedure are restricted: the manifest doesn't say which one is the foreign account, so a procedure that takes a foreign account and an account id as plain data can't be given a sandbox account for the latter. `false` leaves the arguments alone (an account id is plain data), and `null` or a missing flag too: the crash recovery above is the safety net. The account page's Invoke dialog runs on the app's client, where a sandbox account is a valid foreign account, and passes nothing. The crash recovery stays: E2E, `script-simulate.spec.ts` reaches the crash by stripping `callsForeign` from the compile response (`compileWithoutCallsForeign`, `page.route`), then picks an imported counter for `copy_count`, then the simulated one. The tab still refuses an export whose `callsForeign` is `true` (api-compile's MAST walk, stored like `readOnly`) when no dependency resolved: `simulationBlockedReason` (`lib/simulation/blocked.ts`) disables its Invoke button and says why under its name (no account component among the dependencies, one to recompile against, or one whose package isn't in the workspace), through `ProceduresList`'s `blockedReason`, and `simulateProcedure` returns the same error before touching the client when nothing was staged. A `null` (api-compile couldn't tell) or missing flag isn't blocked: its run stages the dependencies too. Note and transaction scripts aren't blocked: they run on the app's client, which fetches a public foreign account from the node.
- The console's tabs are a second `Tabs` inside the page's: scope e2e locators to `getByRole("region", { name: "Editor Console" })`. A compile switches to Output, and so does a failed run. Both panels stay mounted (`keepMounted`), so the log keeps its scroll position and the Simulate tab its arguments.
- E2E: `e2e/script-simulate.spec.ts`. Import the busy public wallet last, and nothing busy before it (Testnet's faucet, say): the target check waits behind the client's sync of such an account, so a recompile after it leaves the dropdown on "Checking accounts…" and the run queued for over a minute. A stale dependency needs a package that is neither the workspace's nor an embedded one: the counter example's original package is embedded, so recompiling the workspace's counter once still resolves. It needs apps/api on 3001 to compile, against an api-compile that returns the schemas: the counter's slot and the P2ID note's typed field come from them. To point a local API at another api-compile, `wrangler dev --port 3001 --var API_COMPILE_URL:<url>` in apps/api: the shell's variable doesn't reach it through `pnpm dev` (turbo) or over `.env.local`.
