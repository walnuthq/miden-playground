# Simulations (the script page's Simulate tab)

The console of an editable script has two tabs: Output (the log) and Simulate, which runs the compiled package locally and shows what it would change. Nothing is proven, submitted or saved. Item 11 of `spec/editor-console-improvements.md` has the plan and the SDK spike's findings.

- Account components run on a throwaway account (basic wallet, No Auth, the component) in a mock client (`lib/simulation/simulation-client.ts`, `MockWasmWebClient`), not the app's client: the SDK can't delete an account and an account's id changes with its storage, so every storage edit would leave an account in the user's store and saved projects. Every mock client opens the IndexedDB store `mock_client_db`; it is deleted when the client is created, once per page load, on the first run.
- Don't run a simulation on the app's client through anything that writes to its store (`newAccount`, `submitNewTransaction`, importing a note). `executeTransaction` and `executeProgram` write nothing, on either client.
- Every run starts from the storage slots shown, at nonce 0. "Apply to storage" in the result dialog copies the resulting values into the slots; nothing else carries state from one run to the next. The account is built on the first run after a compile or a slot edit (`useSimulation`, cached by commitment and slots).
- The slots are in memory, per script (`lib/simulation/simulation-state.ts`), like the console's log: not in `State`, not saved with projects.
- A package's schemas come from api-compile (`storage` and `noteStorage` next to the manifest, `miden-package-metadata/src/schemas.rs` in miden-source-code-verification), stored in the API's `metadata` column and returned as `Script.metadata`. It is null or missing for drafts, failed builds, built-ins, scripts persisted or saved before it existed, and any build by an api-compile older than the schemas: every use falls back.
- With a storage schema the tab lists exactly its slots, at their defaults (`0`, the schema's default word, an empty map) with their descriptions, and offers no slot to add or remove. A recompile keeps the edits of the slots it still has and drops the others (`mergeStorageSlots`, `lib/utils/storage-schema.ts`). Without one the slots start from a workspace component made from the script, else empty, and are added by hand.
- With a note storage schema, a note's storage is one typed field per schema field (`lib/utils/note-storage.ts`), flattened in declaration order as the compiler's `ToFeltRepr` writes them: an account id as its prefix then its suffix (unlike a procedure call's `push.<suffix>.<prefix>`), a word as its four elements, a `u64` as its low then high 32 bits. Verified with the P2ID template: the note is consumed when its field names the target, and its assertion fails otherwise. A field the form can't type (a record the note defines, an option, a variant) turns the whole note back to raw felts, with the schema's fields listed as a hint.
- A run's changes are shown against the simulated account's real initial state (`createSimulatedAccount` returns it), not against the slots: a new account's first transaction reports every slot as created, its other components' included (the storage schema commitment).
- A slot value, a map key or a map value is a felt (a word's first element) or a whole word in hex: `lib/utils/storage-slots.ts`, which `wasmStorageSlotFromStorageSlot` uses for deployed accounts too.
- A state-changing procedure runs twice: as a transaction for its effects, and as a program for its return value, which a transaction doesn't give.
- The raw client's `executeProgram` returns a `FeltArray` (`length()`, `get(i).asInt()`). The React SDK's `useExecuteProgram` converts it; `lib/simulation/run.ts` reads it directly.
- Note and transaction scripts run on the app's client against one of the sandbox's accounts (`useTargetSimulation`, `simulateNote`, `simulateTransactionScript`): a note made from the script, never submitted, is the transaction's unauthenticated input (`withInputNotes` with a `NoteAndArgs`), and a transaction script takes its `Word` argument with `withScriptArg`. The result dialog shows the changes against the account in app state and has no "Apply to storage".
- The target dropdown lists only the accounts whose code has every root in `metadata.accountProcedures` (`useScriptTargetAccounts`). The roots are the account procedures the script `call`s, from api-compile's MAST walk. The checks use `AccountCode.hasProcedure` on the store's account, read only, queued with the simulations. They're cached by code commitment. An account that can't be read is kept. Only the target dropdown is filtered: the note storage's account fields and the Asset dropdown list every account. An absent field or `null` means no filter, and `[]` means every account. When no account qualifies, the hint names the missing procedures from the workspace's scripts, the built-ins and the embedded Rust basic wallet. The P2ID template calls that wallet's `receive-asset`, which no deployed account has unless it was built with that component (tutorial 8's Test Wallet).
- An account whose key isn't in the local keystore can't be simulated: `executeTransaction` and `executeForSummary` both fail on the `miden::protocol::auth::request` event. The log then says to pick a No Auth account or a wallet created here.
- `components/procedures` (the arguments form, the procedures list, the storage slots editor) and `lib/utils/procedure-inputs.ts` know nothing about what runs a procedure: they take handlers. They are meant for the account page's Invoke flow too, which still has its own dialog and hardcoded parameter names.
- The console's tabs are a second `Tabs` inside the page's: scope e2e locators to `getByRole("region", { name: "Editor Console" })`. A compile switches to Output, and so does a failed run. Both panels stay mounted (`keepMounted`), so the log keeps its scroll position and the Simulate tab its arguments.
- E2E: `e2e/script-simulate.spec.ts`. It needs apps/api on 3001 to compile, against an api-compile that returns the schemas: the counter's slot and the P2ID note's typed field come from them. To point a local API at another api-compile, `wrangler dev --port 3001 --var API_COMPILE_URL:<url>` in apps/api: the shell's variable doesn't reach it through `pnpm dev` (turbo) or over `.env.local`.
