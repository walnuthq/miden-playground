# Simulations (the script page's Simulate tab)

The console of an editable script has two tabs: Output (the log) and Simulate, which runs the compiled package locally and shows what it would change. Nothing is proven, submitted or saved. A read-only script has the console too when it holds a package (`canSimulate`, `spec/simulate-read-only-scripts.md`): the read-only scripts a tutorial's starter adds: the counter example's packages (tutorials 6, 9 and 10) and tutorial 10's `count-reader`, assembled from its template. It opens on Simulate; nothing else changes for the script, and "Apply to state" writes to the tab's in-memory slots and vault only. The built-ins assembled from MASM have no package and no console: `basic-wallet` is already on every simulated account (adding it again fails on duplicate procedures), `fungible-faucet` needs a faucet account, authentication components aren't called directly, and the built-in notes' storage is raw felts that can't name the simulated account. On a read-only script, the sentences about an unresolved dependency and `simulationBlockedReason`'s reasons stop at the cause: there's no compile to ask for. Item 11 of `spec/editor-console-improvements.md` has the plan and the SDK spike's findings.

- Account components, and note and transaction scripts on the simulated account, run on a throwaway account (basic wallet, No Auth, the components) in a mock client (`lib/simulation/simulation-client.ts`, `MockWasmWebClient`), not the app's client: the SDK can't delete an account and an account's id changes with its storage, so every storage edit would leave an account in the user's store and saved projects. Every mock client opens the IndexedDB store `mock_client_db`; it is deleted when the client is created, once per page load, on the first run. On the MockChain network (`mmck`, entries still hidden) that store is the sandbox's own (`mockchain-sandbox.md`), so the client is never created there: `hasSimulatedAccounts(networkId)` hides the account component's form (a sentence says to deploy it instead) and the target dropdown's "Simulated account", and `simulationClient()` throws while the tab's client is the sandbox's. On the other networks the client holds a shared Web Lock on the store (`simulationStoreLock`, `lib/mock-chain.ts`) for as long as it lives: a run fails with a message while the sandbox is open in another tab, and a sandbox that starts, in any tab, takes the lock, which discards the client and fails the run in flight. A new feature that needs a mock client goes through `simulationClient()`, never `MockWasmWebClient.createClient()`.
- Don't run a simulation on the app's client through anything that writes to its store (`newAccount`, `submitNewTransaction`, importing a note). `executeTransaction` and `executeProgram` write nothing, on either client.
- Every run starts from the storage slots and the vault shown: at nonce 0, or 1 when the vault holds assets. "Apply to state" in the result dialog copies the resulting values into the slots and the resulting balances into the vault's rows (`applyVaultChanges`); nothing else carries state from one run to the next. The account is built on the first run after a compile, a slot edit or a vault edit (`useSimulation`, cached per client by commitment, slots and vault).
- The vault (`spec/simulate-assets.md`): rows of a simulated asset and an amount (`components/procedures/vault-editor.tsx`), empty by default, so a script that needs no asset gets no seed. `AccountBuilder` can't build an account with assets, so `seedVault` (`lib/simulation/run.ts`) has the new account consume a P2ID note carrying them (the standard basic wallet takes it) and applies that transaction to the mock client's store only, at `getSyncHeight()`: never proven, submitted or put in a block. The mock chain can't hold it: the note was never created on the chain, and `proveBlock` panics on it, then on every later block (a foreign staging's) if it was submitted. Applied to the store alone, every later transaction and program on the account sees the assets, and the chain never learns of it. About 80 ms the first time, 20 ms after. The id doesn't change (it depends on the storage, not the vault). `createSimulatedAccount` returns the state after the seed (`client.getAccount`): the baseline, so the seed never shows as a change. A staged foreign account has no vault: it must be committed, which a store-only seed can't be (minting the note from the faucet in the same block works, 170 ms and a block; no example needs it yet).
- Simulated assets (`lib/simulation/simulated-assets.ts`): a list of symbols per script (`SIM` by default, more through "New asset": 1 to 12 uppercase letters, the faucet's `TokenSymbol`), in memory like the slots (`useSimulatedAssetSymbols`), and one faucet per client and symbol (`mockFaucet(client, symbol)`, about 300 ms, uncommitted, no decimals). The form holds stand-ins (`simulated:asset:<symbol>`, which `simulatedAccountName` refuses: a package name has no colon) wherever a simulation takes an asset or a faucet: the vault's rows, a note's assets, an `Asset` argument (the dropdown's "Simulated" group), an `AccountId` argument or a typed note storage field (as "<symbol> faucet"). The hooks make the faucets the run uses (`mockFaucetIds`), resolve the stand-ins before encoding (`resolveSimulatedAsset`), and return `faucetLabels` for the result dialog and `vaultChanges` (final balances by stand-in) for "Apply to state". A sandbox account takes none: its run refuses them, and switching to one clears the note's assets.
- An `Asset` argument's id is the faucet's prefix and its suffix plus `0x11` (composition fungible, version 1, as `FungibleAsset.vaultKey()` gives it): another value is an id no vault holds, and a balance read gives zero.
- The slots are in memory, per script (`lib/simulation/simulation-state.ts`), like the console's log: not in `State`, not saved with projects.
- A MASM package carries no schema: a script's `storage` and `noteStorage` are hand-written ones, for the templates and the examples' packages (`script-templates.md`, "Hand-written schemas"), set by the API in the `metadata` column and returned as `Script.metadata`. They're missing for a script written from a blank template, an import, a script whose source stopped matching its schema, and a package verified through api-registry (the registry stores none): every use falls back. The built-ins assembled from MASM carry a hand-written `storage` (`lib/types/default-scripts/storage-schemas.ts`, the slots of their SDK components).
- An account component without a `storage` schema has `metadata.slotNames` instead: the names its source declares with `word("…")`, read by the API on each build (`lib/storage-slot-names.ts`). The tab and the Deploy Account dialog start from them (`initialSlotsOf`, `lib/utils/storage-schema.ts`), each as a value at `0`: the source doesn't say whether a slot is a map, so the raw editor sets each slot's type ("<name> type"), and a `word("…")` that isn't a slot is removed by hand. A name a later compile brings joins the edited slots once (`useSimulationStorageSlots`' `declared`): a slot the user removed stays removed.
- With a storage schema the tab lists exactly its slots, at their defaults (`0`, the schema's default word, an empty map) with their descriptions, and offers no slot to add or remove. A recompile keeps the edits of the slots it still has and drops the others (`mergeStorageSlots`, `lib/utils/storage-schema.ts`). Without one the slots start from the names the source declares (above), or empty, and are added, removed and typed by hand. A script that had a custom component before components were removed gets that component's slots as its schema (`migrateLegacyComponents`, `saved-projects.md`) until its next compile.
- With a note storage schema, a note's storage is one typed field per schema field (`lib/utils/note-storage.ts`), flattened in declaration order, as the templates' MASM reads them: an account id as its prefix then its suffix (unlike a procedure call's `push.<suffix>.<prefix>`), a word as its four elements, a `u64` as its low then high 32 bits. Verified with the P2ID template: the note is consumed when its field names the target, and its assertion fails otherwise. A field the form can't type (a record the note defines, an option, a variant) turns the whole note back to raw felts, with the schema's fields listed as a hint. The block is one component, `components/procedures/note-storage-fields.tsx`, shared with the Create Note dialog: it takes values and handlers and knows nothing of what runs.
- A run's changes are shown against the simulated account's real initial state (`createSimulatedAccount` returns it), not against the slots: a new account's first transaction reports every slot as created, its other components' included (the storage schema commitment).
- A slot value, a map key or a map value is a felt (a word's first element) or a whole word in hex: `lib/utils/storage-slots.ts`, which `wasmStorageSlotFromStorageSlot` uses for deployed accounts too.
- A state-changing procedure runs twice: as a transaction for its effects, and as a program for its return value, which a transaction doesn't give.
- The raw client's `executeProgram` returns a `FeltArray` (`length()`, `get(i).asInt()`). The React SDK's `useExecuteProgram` converts it; `lib/simulation/run.ts` reads it directly.
- Note and transaction scripts run against a target picked in the tab (`useTargetSimulation`, `simulateNote`, `simulateTransactionScript`): a note made from the script, never submitted, is the transaction's unauthenticated input (`withInputNotes` with a `NoteAndArgs`), and a transaction script takes its `Word` argument with `withScriptArg`. A sandbox account runs on the app's client, and the result dialog shows the changes against the account in app state, with no "Apply to state".
- The target dropdown's "Simulated account" (`spec/simulate-throwaway-target.md`) runs on the mock client instead: a throwaway account (`createSimulatedAccount`) with the standard basic wallet, No Auth, and one component per `account-component` dependency of the script that resolves (`foreignDependencies`, the same resolution as foreign accounts; none gives a bare No Auth wallet). It's never committed: an account at nonce 0 the chain never saw runs a transaction script or consumes an unauthenticated note all the same. Its storage is edited under the form, one editor per dependency, in `useDependencyAccounts`'s slots (`${scriptId}:foreign:${dependencyName}`: a script is either an account component or a note or transaction script, so the keys never clash), and "Apply to state" applies the result to each dependency's slots and to the vault. It has one vault, whatever its dependencies, edited above their storage and keyed by the script's id like an account component's (a script is one kind or the other). It's cached per client by each component's commitment and slots and by the vault, like an account component's. Its id changes with every edit, so the form holds stand-ins (`SIMULATED_TARGET`, `lib/simulation/simulated-target.ts`, and the simulated assets' stand-ins), resolved during the run: a typed account field of the note's storage can name it, raw felts can't. A dependency is the target's by default. Its "Foreign account" switch (`DependencyAccounts`' `foreign`, `useForeignDependencyNames` in `simulation-state.ts`, in memory per script) makes it another account instead, for a note or transaction script that makes a foreign call: the package doesn't say which dependency is called on another account (their `callsForeign` is `null`), so the user does. `useTargetSimulation` then stages it like an account component's foreign account (`stageForeignAccount`, the same cache key) before building the target, which no longer holds its component, and "Apply to state" leaves its slots alone (a foreign call only reads). A typed account field of the note's storage names it in the dropdown's "Simulated" group (`simulated:<dependency name>`, resolved by `resolvingAccountIdParts`; a field naming a dependency that isn't marked fails the run with a message). A transaction script or a raw-felt note can only name it by its id, which each run writes to the log ("Foreign account <name>: 0x…"): it's stable until its slots are edited or the mock client is reset. E2E: the last-but-one step of the note test in `script-simulate.spec.ts` rewrites `increment-note` to read the counter through FPI. When the script's `accountProcedures` name a root none of its components has, the intro names them (`simulatedTargetMissing`), but the account stays offered: a note that calls a missing procedure only fails when it reaches the call. Switching between it and a sandbox account clears the note's assets and any account field naming it or a simulated asset's faucet.
- A note's asset makes the client load its faucet as a foreign account: from the client's own store first, then from the RPC (`fetch_public_account_inputs`, miden-client 0.17.5 `src/transaction/mod.rs`), which on the mock client panics on an id its chain doesn't hold. So on the simulated account a note carries only simulated assets (above), never a sandbox faucet's: the form takes amounts in base units, and the result dialog shows the same numbers. A reset client makes new faucets. The result dialog names them through `faucetLabels` ("Simulated asset" and the symbol): they aren't in app state. A note carries a list of assets (`clientCreateNoteFromScript`'s `assets`), the same rows as the vault.
- A note whose script doesn't take the asset it carries fails the kernel's last check, on either client: the assets of the account and the notes must add up to the same total before and after (`ERR_EPILOGUE_TOTAL_NUMBER_OF_ASSETS_MUST_STAY_THE_SAME`, miden-protocol 0.17.1 `asm/kernels/transaction-core/src/epilogue.masm`). The executor reports only its code, 4544980346559459778: the first felt of the Blake3 hash of the assertion's message (`error_code_from_msg`, miden-core). `targetErrorHint` (`lib/simulation/run.ts`) matches that code and adds the explanation to the log, as it does for a missing key, and for code 644413868907058392 (`ERR_VAULT_FUNGIBLE_ASSET_AMOUNT_LESS_THAN_AMOUNT_TO_WITHDRAW`: more removed than the vault holds), on every run, a procedure's included. To name a new code, hash the `ERR_*` messages of the `asm` directories of `miden-protocol` and `miden-standards` at that version (0xMiden's protocol repository) with Blake3 (`@noble/hashes`) and take the first 8 bytes, little-endian, modulo the field's prime. The counter example's increment note is such a note. After an SDK bump, `script-simulate.spec.ts` fails on the hint if the message, and so the code, changed.
- The target dropdown lists only the sandbox accounts whose code has every root in `metadata.accountProcedures` (`useScriptTargetAccounts`), and always offers the simulated account above them, preselected once the filter has settled when no sandbox account qualifies. The roots are the account procedures the script `call`s, from api-compile's MAST walk. The checks use `AccountCode.hasProcedure` on the store's account, read only, queued with the simulations. They're cached by code commitment. An account that can't be read is kept. Only the target dropdown is filtered: the note storage's account fields and the Asset dropdown list every account. An absent field or `null` means no filter, and `[]` means every account. Procedures are named from the workspace's scripts and the built-ins. The P2ID template calls the standard `receive_asset`, which every wallet and the built-in basic wallet have.
- An account whose key isn't in the local keystore can't be simulated: `executeTransaction` and `executeForSummary` both fail on the `miden::protocol::auth::request` event. The log then says to pick a No Auth account or a wallet created here.
- A procedure's arguments are named from the MASM source (`procedureParams`, `lib/utils/procedure-inputs.ts`): the export's `parameters` (`read-only-procedures.md`), as the source spells them, and `param_0`, `param_1`… for every parameter when the list is missing, has another length than the signature's, or holds an empty or repeated name: never a mix. The signature lines (`procedureSignature`, the procedures list and the Manifest tab's exports table) show `proc name(name: Type) -> Type` with names and the types alone without; the exports table wraps them. `ProcedureArguments` is keyed by these names, so a recompile that brings names drops the values typed under `param_N`, once: the forms' state is in memory, nothing saved holds it.
- The forms read the manifest's layouts as miden-assembly writes them (`fixtures/masm-manifests.json` holds the templates' and a probe's, captured from the local api-compile): `"Felt"` is a felt, `{ Array: { ty: "Felt", len: 4 } }` a word, the `AccountId` and `Asset` structs the account picker and the asset input (`knownType`). An integer below a felt (`U8`, `U16`, `U32`), a `bool` (`I1`) and an enum without values (`NoteType`, its discriminant) are a `Felt` input with a bound (`ProcedureParam.max`, label `NoteTag (u32)`, `Bool (0 or 1)`, `NoteType (0 PRIVATE, 1 PUBLIC)`). Anything else whose layout flattens to felts (a struct the source defines, a `u64` as its low then high limb, as miden-core-lib takes it) is entered as raw felts (`feltLeaves`, `spec/raw-felt-arguments.md`), one input per felt named by field path, under "Entered as raw felts: the form doesn't know this type."; only a layout without fields or an enum with values has no input. Felts are pushed last first, so a layout's first field ends on top: an `AccountId` is `struct { suffix, prefix }` in miden-protocol 0.18, so the typed one pushes `push.<prefix>.<suffix>` (the suffix on top, as `tx::execute_foreign_procedure` and `count-reader` take it), and an `Asset` its id word `[0, 0, suffix, prefix]` then its value word `[amount, 0, 0, 0]`. `script-simulate.spec.ts` checks both against raw felts, and the foreign call through FPI. A result is decoded as a felt or a bounded integer in decimal, a word in hex, anything else as its felts. A type the source exports (`pub type`) is a `{ Type: … }` entry of the manifest's exports, which the API drops (`analyzedExports`). A call passes at most 16 felts (`MAX_ARGUMENT_FELTS`).
- A procedure that declares no signature (`pub proc add`, its stack effect in a comment) has a null signature in the manifest. The API keeps it with an empty one and `untyped: true` (`analyzedExports`), and `typedProcedureExport` (`lib/utils/script.ts`) does the same for a registry package. `procedureParams` gives it one parameter, `stack` (`ProcedureParam.stack`): a text field of up to 16 felts separated by spaces or commas, the top of the stack first, empty for none (the `Stack` argument, encoded as `Felts`). Its row shows `proc add`, and its result is the stack it leaves without its padding zeros (`procedureResult`), read even for a state-changing one since the manifest doesn't say whether it returns anything. Read `procedureExport.signature` only through these helpers.
- Every deployed account carries the built-in basic wallet (`lib/types/default-scripts/basic-wallet.ts`, assembled from MASM), and the account page offers Invoke on its procedures for a No Auth account. Its exports carry hand-written signatures and parameter names, laid out as api-compile lays out the basic-wallet template's (`apps/api/templates/basic-wallet.masm`, the same procedures instruction for instruction), so the dialog asks for `create_note`'s tag (a `u32`), note type (an enum) and recipient (one word), and `move_asset_to_note`'s asset and note index (a `u16`): the integers and the enum as bounded felts. The other built-ins (the faucet, the authentication components) have no signature: invoked, they get an empty stack. A component assembled from MASM is linked as `external_contract::<name>` and its procedure called by the last segment of the export's path (`invokeProcedureCustomTransactionScript`, `lib/utils/script.ts`): the built-ins' paths are their full paths in the standards library, which can't follow `<name>::`. E2E: tutorial 10's spec previews the built-in `create_note` on the Count Reader's account.
- `components/procedures` (the arguments form, the procedures list, the storage slots editor) and `lib/utils/procedure-inputs.ts` know nothing about what runs a procedure: they take handlers. The account page's Invoke dialog (`components/account/invoke-procedure-arguments-dialog.tsx`) uses the same form and encoding, and `decodeProcedureResult` for a read-only call's result.
- A procedure that calls another account's procedure (FPI) runs against a foreign account staged on the mock chain (`spec/simulate-foreign-calls.md`). The mock client's RPC serves only the accounts committed on its chain, and its lazy fetch finds them without a declaration, as on a real network. One account is staged per `account-component` dependency of the script whose package resolves (`foreignDependencies`, `lib/simulation/foreign-accounts.ts`), in this order: a workspace script with the same id, `masp` and `commitment`; any workspace script with that `commitment` and a `masp` (a `count-reader` made from its template depends on the `counter-account` template, whose dependency carries the API's built-in id: in tutorial 10 it resolves to the counter example's `counter-account` the starter adds, the same source under the same name); a built-in dependency's package from the API (`BUILT_IN_DEPENDENCY_IDS`: `counter-account`, which a `count-reader` made alone from its template depends on; `GET /scripts/dependencies/:name` builds it from the template, with the template's schema, and `useBuiltInDependencies` in `lib/simulation/built-in-dependencies.ts` asks for it once per page load, only when the workspace doesn't resolve it, and keeps it in memory: about 530 KB, never in `State`; the dependency isn't reported unresolved while the request is running). `basic-wallet` isn't asked for: every simulated account carries the standard wallet, whose procedures are the template's. A dependency's `commitment` is its package as the script was compiled against it: a workspace script with the same id and another commitment was recompiled since, its procedure roots aren't those the script calls, and it doesn't resolve ("stale": the tab asks to recompile the script). A staged account is a simulated account (`createSimulatedAccount`) made from the dependency's package and the slots of the tab's "Foreign accounts" block (keyed `${scriptId}:foreign:${dependencyName}` in `simulation-state.ts`, starting slots as for the script's own), then committed by `stageForeignAccount` (`lib/simulation/run.ts`): an empty transaction (No Auth bumps a new account's nonce), `proveTransaction` (a dummy proof on the mock client), `submitProvenTransaction`, `applyTransaction`, `proveBlock()`, `syncState()`. About 100 ms the first time, 40 ms after. Staging happens at Invoke, before the caller's account, never on a slot edit, and not for a procedure whose `callsForeign` is `false` unless an argument names a staged account: each staging adds an account and a block. It's cached per client by commitment and slots, like the caller. An `AccountId` argument picks a staged account in the dropdown's "Simulated" group (`SelectAccountDropdownMenu`'s `simulatedAccounts`): its id changes with every slot edit, so the form holds a stand-in (`simulated:<dependency name>`) that `useSimulation` replaces with the staged id before encoding. Several foreign accounts coexist, and an older one stays usable after an edit stages a new one. Only one level: a staged account's own dependencies aren't staged.
- The mock RPC keeps a snapshot of the chain per block, so runs slow down as stagings pile up: about 370 ms a run (staging and caller included) after the first, 520 ms after 50 (measured 2026-11-16). After `STAGINGS_PER_CLIENT` (100) stagings, `withSimulationClient` discards the client once the run is over, and the next run starts a new one.
- A sandbox account is still out of the mock chain's reach: picked as a foreign call's account, it makes the mock RPC panic (`committed_account(account_id).unwrap()`, miden-client 0.17.5 `test_utils/mock.rs:748`). The panic happens inside the client's worker, and the SDK never settles the call: left alone, the row stays on "Invoking…" and every later simulation waits behind it in `enqueueSimulation`'s queue (account components, notes, transaction scripts and the target filter alike) until a reload. So every mock-client run goes through `withSimulationClient` (`lib/simulation/simulation-client.ts`): the worker's `error` event (caught about a second after the panic; `client.worker` isn't in the SDK's typings) or a 60 s timeout discards the client and calls `terminate()`, which rejects the hung call ("WebClient terminated"), and the run fails with a message saying the client was reset. The next run creates a new client, whose store starts empty: `useSimulation` caches simulated and staged accounts per client, so they're built again. So the tab doesn't offer one where it knows better: for an export whose `callsForeign` is `true`, every `AccountId` argument lists the sandbox's accounts disabled, with the reason as a line in the menu (`sandboxAccountsDisabledReason`, `lib/simulation/blocked.ts`, passed to `ProceduresList` as `sandboxDisabledReason` and down to `SelectAccountDropdownMenu`), and only the "Simulated" group can be picked. A sandbox account picked before the rule applied (a recompile that brought the flag) is cleared (`withAccountIdsAmong`, `lib/utils/procedure-inputs.ts`). All the `AccountId` arguments of such a procedure are restricted: the manifest doesn't say which one is the foreign account, so a procedure that takes a foreign account and an account id as plain data can't be given a sandbox account for the latter. `false` leaves the arguments alone (an account id is plain data), and `null` or a missing flag too: the crash recovery above is the safety net. The account page's Invoke dialog runs on the app's client, where a sandbox account is a valid foreign account, and passes nothing. The crash recovery stays: E2E, `script-simulate.spec.ts` reaches the crash by stripping `callsForeign` from the compile response (`compileWithoutCallsForeign`, `page.route`), then picks an imported counter for `copy_count`, then the simulated one. The tab still refuses an export whose `callsForeign` is `true` (api-compile's MAST walk, stored like `readOnly`) when no dependency resolved: `simulationBlockedReason` (`lib/simulation/blocked.ts`) disables its Invoke button and says why under its name (no account component among the dependencies, one to recompile against, or one whose package isn't in the workspace), through `ProceduresList`'s `blockedReason`, and `simulateProcedure` returns the same error before touching the client when nothing was staged. A `null` (api-compile couldn't tell) or missing flag isn't blocked: its run stages the dependencies too. Note and transaction scripts aren't blocked: they run on the app's client, which fetches a public foreign account from the node.
- The console's tabs are a second `Tabs` inside the page's: scope e2e locators to `getByRole("region", { name: "Editor Console" })`. A compile switches to Output, and so does a failed run. Both panels stay mounted (`keepMounted`), so the log keeps its scroll position and the Simulate tab its arguments.
- E2E: `e2e/script-simulate.spec.ts`. Import the busy public wallet last, and nothing busy before it (Testnet's faucet, say): the target check waits behind the client's sync of such an account, so a recompile after it leaves the dropdown on "Checking accounts…" and the run queued for over a minute. A stale dependency needs a workspace script of the dependency's id with another commitment: a built-in dependency is only asked from the API when the workspace holds no script of that id. It needs apps/api on 3001 to compile and to serve the built-in counter's package ("a Count Reader alone simulates its foreign call"). To point a local API at another api-compile, `wrangler dev --port 3001 --var API_COMPILE_URL:<url>` in apps/api: the shell's variable doesn't reach it through `pnpm dev` (turbo) or over `.env.local`.
- The Create Note dialog (`components/notes/create-note-dialog.tsx`, `spec/create-note-preview.md`) types a note's storage with the same component, under stricter rules (`createNoteStorageParams`, `lib/utils/note-storage.ts`): typed fields only for a compiled script whose schema types every field, raw felts for a draft, a failed compile, a script compiled before api-compile returned schemas (a saved project, a resumed tutorial run) or an untypable schema. Tutorial 8's edited note has no schema (a note loses its template's on any edit), so its step 4 gives the raw items. An "Enter as raw felts" switch turns typed fields into raw ones, prefilled with their felts when they're all valid (an account field lists the sandbox's accounts only, raw felts can name any). Changing the script resets the storage. Create and Preview stay disabled while a field is empty or invalid. The dialog flattens before calling `newNote`, whose `noteStorage: string[]` is unchanged. Verified on testnet with tutorial 8: the typed note's storage is the Test Wallet's prefix, suffix, then the height, and the Test Wallet consumes it.
- Its "Preview consumption" button (`hooks/use-note-preview.ts`) runs `simulateNote` on the app's client, through `enqueueSimulation` and `runOnSandboxAccount` (shared with the Simulate tab's sandbox runs): the recipient consumes a note with the dialog's sender (the connected wallet), type, network flag, asset and storage, executed only. The result opens `SimulationResultDialog` with its own title and description and no "Apply to state"; a failure shows its cleaned error under the form, until a field changes, and never disables Create. Checked 2026-11-17: a sender other than the consumer works; a network account runs it locally, as a regular or a network note; a sandbox faucet's asset loads the faucet from the node. The account and note tables are unchanged, but executing caches the faucet's code (`accountCode`, `foreignAccountCode`), as any transaction with that asset does. A timelocked note before its height fails on its own assertion, which has no message (`assertion failed with error code: 10154102372021603817`): the dialog shows the code only. The connected wallet isn't offered as a recipient (unless it signs a multisig), so a recipient whose key is in Bread or Para only comes in imported, and fails on `miden::protocol::auth::request` with the existing hint. A preview can't tell whether the sender can fund and pay for the note, the state at consumption time (another block, other notes consumed first), or anything about a recipient the sandbox doesn't track or whose key isn't in the Playground. `storeRecordCounts` (`e2e/store.ts`) counts the tables a preview must leave alone.
