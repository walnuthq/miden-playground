# Simulations (the script page's Simulate tab)

The console of an editable script has two tabs: Output (the log) and Simulate, which runs the compiled package locally and shows what it would change. Nothing is proven, submitted or saved. Item 11 of `spec/editor-console-improvements.md` has the plan, what's left (note and transaction scripts, the storage schema from api-compile) and the SDK spike's findings.

- Account components run on a throwaway account (basic wallet, No Auth, the component) in a mock client (`lib/simulation/simulation-client.ts`, `MockWasmWebClient`), not the app's client: the SDK can't delete an account and an account's id changes with its storage, so every storage edit would leave an account in the user's store and saved projects. Every mock client opens the IndexedDB store `mock_client_db`; it is deleted when the client is created, once per page load, on the first run.
- Don't run a simulation on the app's client through anything that writes to its store (`newAccount`, `submitNewTransaction`, importing a note). `executeTransaction` and `executeProgram` write nothing, on either client.
- Every run starts from the storage slots shown, at nonce 0. "Apply to storage" in the result dialog copies the resulting values into the slots; nothing else carries state from one run to the next. The account is built on the first run after a compile or a slot edit (`useSimulation`, cached by commitment and slots).
- The slots are in memory, per script (`lib/simulation/simulation-state.ts`), like the console's log: not in `State`, not saved with projects. Until the API returns the package's storage schema they start from a workspace component made from the script, else empty, and slots are added by hand.
- A run's changes are shown against the simulated account's real initial state (`createSimulatedAccount` returns it), not against the slots: a new account's first transaction reports every slot as created, its other components' included (the storage schema commitment).
- A slot value, a map key or a map value is a felt (a word's first element) or a whole word in hex: `lib/utils/storage-slots.ts`, which `wasmStorageSlotFromStorageSlot` uses for deployed accounts too.
- A state-changing procedure runs twice: as a transaction for its effects, and as a program for its return value, which a transaction doesn't give.
- The raw client's `executeProgram` returns a `FeltArray` (`length()`, `get(i).asInt()`). The React SDK's `useExecuteProgram` converts it; `lib/simulation/run.ts` reads it directly.
- An account whose key isn't in the local keystore can't be simulated: `executeTransaction` and `executeForSummary` both fail on the `miden::protocol::auth::request` event.
- `components/procedures` (the arguments form, the procedures list, the storage slots editor) and `lib/utils/procedure-inputs.ts` know nothing about what runs a procedure: they take handlers. They are meant for the account page's Invoke flow too, which still has its own dialog and hardcoded parameter names.
- The console's tabs are a second `Tabs` inside the page's: scope e2e locators to `getByRole("region", { name: "Editor Console" })`. A compile switches to Output, and so does a failed run. Both panels stay mounted (`keepMounted`), so the log keeps its scroll position and the Simulate tab its arguments.
- E2E: `e2e/script-simulate.spec.ts`. It needs apps/api on 3001 to compile.
