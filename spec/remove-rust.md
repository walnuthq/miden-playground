# Remove Rust: back to plain MASM

Status: analysis and spike, 2026-11-24. Nothing is implemented. The decisions were taken with the user on 2026-11-24 and are recorded in [Decisions](#decisions). The spike ran the same day: its results are in [Spike results](#spike-results), and the one question it couldn't answer, whether upstream plans a storage schema for MASM projects, is closed by assumption: there is none (decision 3).

The Miden Rust compiler (`cargo-miden`, `midenc`, the `miden` SDK crate) is being phased out. The Playground (this repo) and the source code verification system (`walnuthq/miden-source-code-verification`, "the verifier" below) must both stop compiling, storing, showing and teaching Rust, and work from Miden Assembly sources instead.

This document says what that means for each project, what replaces each Rust-specific piece, what is lost, and in which order the work can ship.

## Summary

- **The package model survives.** Upstream already builds MASM projects into `.masp` packages: a `miden-project.toml` with `[lib] path = "<file>.masm"` is assembled by `miden-assembly`'s `ProjectAssembler`. miden-standards 0.18 is built this way. Both projects can keep everything keyed on a package (commitment, manifest, exports, dependencies) and swap only how the package is built.
- **api-compile changes the most, and gets much simpler.** `cargo miden build` becomes an in-process assembly that takes milliseconds and runs no project code. The Rust toolchain, the warm cargo cache, the lockfile plumbing, the build-isolation machinery and the release/debug split all lose their reason to exist.
- **Three things the Rust toolchain embedded in a package have no MASM equivalent today**: an account component's storage schema, a note's storage schema, and procedure parameter names. The Playground's deploy form, Simulate tab and argument forms, and the verifier's viewer, all read them. This is the main design problem, not the build swap.
- **The Playground's content is Rust**: 10 templates, 2 examples (6 packages), tutorials 6 to 12, 3 embedded packages, and the e2e specs that drive them. All of it has to be rewritten in MASM. This is the largest share of the work.
- **Stored Rust data can't be rebuilt any more**: the Playground's `packages` rows, scripts in users' browsers, shared links and project links, and the registry's verified records. Decided: all of it is deleted, the Playground's at its switch to MASM and the registry's when cargo leaves api-compile (decisions 2, 6 and 13).
- **Several workarounds disappear**: the Rust basic wallet that tutorial 8 embeds (a MASM P2ID note calls the standard wallet's own procedures), the template lockfile sync, the weekly lockfile drift check, the slow-compile failure mode.

## Scope and assumptions

- "Rust" means the Miden Rust compiler pipeline and Rust as a contract language. api-compile's three helper tools (`miden-import`, `miden-verifier`, `miden-package-metadata`) are Rust programs built on `miden-client` and the VM crates. They are not part of the compiler and they stay (decision 1).
- The upstream phase-out is taken as given: I have no upstream announcement or timeline to cite, and didn't look for one. What I checked is what upstream ships for MASM today (next section).
- `walnuthq/miden-verify` (the `miden verify` CLI, distributed through midenup) uploads `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml` and `.cargo/config.toml`. It is a third project with the same problem and must change with the verifier's API (see [Other repositories](#other-repositories)).

## What upstream offers for MASM

Read in the crates.io sources on this machine (`miden-assembly` 0.36.4, `miden-project` 0.36.4, `miden-protocol` and `miden-standards` 0.18.0) and in `@miden-sdk/miden-sdk` 0.18.0.

| Need                          | What exists                                                                                                                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A MASM project format         | `miden-project.toml`: `[package]`, `[lib] kind / namespace / path`, `[dependencies]`, workspaces. The same file the Rust projects already carry, with `path` naming the root `.masm` module and `namespace` a MASM path (`miden::standards::…`), not a WIT name.                |
| Package kinds                 | `library`, `kernel`, `account-component`, `note`, `tx-script` (alias of `transaction-script`): the kinds both projects already store.                                                                                                                                           |
| Building a `.masp`            | `Assembler::for_project_at_path(manifest, registry).assemble(selector, profile)` then `Package::write_masp_file`. `miden-protocol-build-utils::assemble_project` wraps it. Dependencies resolve against a `PackageCache` seeded with the core, protocol and standards packages. |
| Dependencies between projects | Path dependencies (`{ path = "../counter" }`) are assembled first and linked, dynamically by default, statically with `linkage = "static"`. This is what the Playground's script dependencies map to.                                                                           |
| Profiles                      | `dev` keeps a `DEBUG_INFO` section, `release` drops it (`miden-assembly` project tests). miden-standards publishes `dev` packages.                                                                                                                                              |
| Typed signatures              | MASM procedures declare typed, named parameters: `pub proc receive_asset(asset: Asset)`, `pub proc move_asset_to_note(asset: Asset, note_idx: u16)`.                                                                                                                            |
| Deploying from a MASM package | The web SDK's `AccountComponent.fromPackage(package, slots)` builds its own metadata and doesn't need a metadata section (`web-sdk`, `crates/web-client/src/models/account_component.rs`). `NoteScript.fromPackage` and `TransactionScript.fromPackage` take a package too.     |
| Assembling in the browser     | `client.compile.component / txScript / noteScript` and `CodeBuilder` assemble MASM in WASM. They return a component, a script or a `Library`, never a `.masp`: `Package` only has `deserialize` and `serialize`.                                                                |

What a MASM-built package does not contain, checked in `miden-assembly` (the only sections it writes are `DEBUG_INFO`, `KERNEL` and `PROJECT_SOURCE_PROVENANCE`):

| Rust toolchain embedded                                              | Read by                                  | In a MASM package                                                                                                                             |
| -------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `ACCOUNT_COMPONENT_METADATA` (storage slots: names, types, defaults) | `schemas.rs` → `storage`                 | Absent. miden-standards attaches it from Rust code, per component, after assembly.                                                            |
| `note_storage_schema` (WIT record of a note's inputs)                | `schemas.rs` → `noteStorage`             | Absent, and WIT goes away with the compiler.                                                                                                  |
| `wit` (the component's public interface)                             | `parameters.rs` → `parameters`           | Absent. The names are in the MASM source; the manifest's signature has the types only (spike), so they are read from the source (decision 4). |
| The compiler's MASM (`--emit masm`)                                  | `masm: true` → the Playground's MASM tab | The source is the MASM.                                                                                                                       |

The three MAST analyses (`read_only.rs`, `foreign_calls.rs`, `account_procedures.rs`) walk the package's MAST and don't depend on the source language. They should carry over; their tests are written against Rust-built fixtures and need new ones.

The five points this section used to list as unverified were checked in the spike, except upstream's plans for a storage schema, assumed to be none (decision 3): see [Spike results](#spike-results).

## The one architectural choice: where the Playground assembles

| Option                            | How                                                                                                          | For                                                                                                                                                    | Against                                                                                                                                                                                              |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Server, as today (recommended) | `PATCH /scripts/:id` → api-compile assembles the project → `.masp`, manifest, analyses.                      | One builder for the Playground and the verifier, so what the Playground deploys is what `/verify` rebuilds. The data model, API and store shapes stay. | Still a round trip and a container that sleeps, though a build is milliseconds once it's awake.                                                                                                      |
| B. Browser                        | The SDK's `CodeBuilder` assembles on every edit; the API only stores sources.                                | Instant diagnostics, works offline and on MockChain with no API.                                                                                       | No `.masp`, no manifest, none of the three analyses, no storage schema. No verified package to show for tutorial 12, though the spike found the same roots from `CodeBuilder` and the project build. |
| C. The assembler as WASM          | Compile the project assembler and `miden-package-metadata` to WASM, run it in the API Worker or the browser. | A's output without the container: no cold start.                                                                                                       | A new build target to maintain; `miden-import` and `miden-verifier` need `miden-client` with a store and stay in the container anyway.                                                               |

Decided: A (decision 11). It is the smallest change and keeps verification honest. B could be added later on top of A as live diagnostics only (the server build stays the source of truth), and C is an optimisation to consider once A is measured. Neither is planned.

Toolchain note: api-compile is on the 0.17 toolchain (`cargo-miden` 0.11.0, VM crates 0.35, `miden-client` 0.17.5) while the Playground's web SDK is 0.18.0. A MASM build links against the protocol and standards packages, so its roots depend on their version. The MASM build should target the crates matching the networks served, and plan 025 (more than one toolchain) becomes cheap: an assembler per protocol version is a few megabytes, not a rustup toolchain plus a 1.6 GB cache. The spike adds two facts: the `miden-protocol` and `miden-standards` 0.18.0 crates ship packages versioned 0.17.2, and `miden-core-lib` 0.36.4 one versioned 0.36.3, so a project's dependency versions name the package, not the crate; and the 0.35-based `miden-package-metadata` reads a 0.36 release package but not a dev one (`unsupported debug_info version: 4, expected 3`), so the helper tools need the 0.36 bump before debug info can be kept.

### api-registry

- `packages` table: `built_with` and `debug_built_with` are documented as cargo-miden versions; `parameters` as read from WIT; `files` holds `Cargo.lock`. The columns can stay with new meanings. Rust rows and MASM rows coexist only between steps 3 and 6 of the rollout: the Rust-built packages and their verified records are deleted when cargo leaves api-compile (decision 6), so no discriminator column is needed. During that window a row is Rust-built when its `files` hold a `Cargo.toml`.
- Admin routes that rebuild from stored sources (the debug-build backfill, `registry-backfill.md`) stop working for Rust rows once cargo-miden leaves the image. Any backfill of a new column must read the stored `.masp`, which the guide already prefers.
- The OpenAPI annotations (`app.ts`, `routes/v1/*.ts`) describe a "compiled Rust source package", `Cargo.toml` and `Cargo.lock`: rewrite, and republish the docs.
- `packageMaspPath` names the download "as Rust spells the crate" (`counter_contract.masp`): decide the MASM spelling.

### web-verifier

- `collect-project-files.ts` is a port of `miden-verify`'s file filter: it keeps `src/**`, `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`, `.cargo/config.toml`, and finds packages by their `Cargo.toml`. It becomes `miden-project.toml` plus `**/*.masm`, and finds packages by `miden-project.toml`.
- The form's copy ("Select the folder of the Rust project to verify").

### web-viewer

- Source code: Shiki highlights `.rs` as Rust and everything else as TOML (`package-sources.server.ts`), the file list keeps `Cargo.toml`, `miden-project.toml` and Rust sources (`source-files.ts`), and finds a package's directory by its `Cargo.toml`. It needs a MASM grammar for Shiki (a TextMate grammar; the Playground's Monarch tokenizer and its `vocabulary.json` are the closest thing we own) and the new file rules.
- Procedure signatures are written as Rust (`procedure-signatures.ts`: `fn deposit(depositor: AccountId) -> …`, `rustType`). They become MASM signatures.
- Rust records exist until they are deleted (decision 6), so the viewer shows both kinds between steps 3 and 6, and loses its Rust rendering in step 6.

### The rest

- `apps/status-page`: the probe compiles and verifies a fixture and describes the service as compiling Rust.
- `README.md`, `GLOSSARY.md` (Project, Build, Debug build, Helper tool, Package), `CODING_STANDARDS.md`, `MIGRATION.md`, `CLAUDE.md` and `docs/claude/` (`warm-lockfile.md` goes; `debug-builds.md`, `deploys.md`, `local-development.md`, `testing.md` shrink).
- `spec/masp-reproducibility.md` and its patch, `spec/procedure-parameters.md` and `spec/upstream-miden-issues.md` describe compiler behaviour: mark them historical.
- Deploy: `deploy-api-compile-cloudflare.yml` warms an image cache that takes 30 min cold. The container's instance type (`standard-2`, chosen for the cache and cargo) can be revisited once the image is small. The 50 s cold start should drop with the image; measure it.

### Web app (`apps/web`)

- **Script model** (`lib/types/script.ts`, `lib/utils/script-files.ts`, `lib/utils/script.ts`): `SCRIPT_FILE = "src/lib.rs"`, `scriptFilePaths`, `PackageSource.rust`. `Script.masm` and `assembledFromMasm` exist because a compiled Rust script has both a package and compiler MASM while a built-in has MASM only. With MASM sources that distinction can collapse: a built-in and a user script are the same kind of thing (decision 8).
- **Editor** (`components/lib/editor.tsx`, `components/script/*`): the source file's language is Rust; the MASM tab is a read-only view of `script.masm`. The source editor becomes the MASM editor, with the existing Monarch language (`lib/masm/language.ts`). The MASM tab goes. The file explorer shows two files. `e2e/script-masm.spec.ts` pins token types on the tab and moves to the editor.
- **MASM vocabulary** (`pnpm masm:sync`): it reads the `miden-assembly-syntax` tag from `apps/api/templates/project-template/Cargo.lock`, which disappears. It needs another source for the version (api-compile's `GET /`, or a pinned constant bumped with the SDK). `docs/claude/masm-highlighting.md` and `drift.yml` follow.
- **Diagnostics** (`lib/utils/diagnostics.ts`, `compiler-output.ts`, six fixtures under `fixtures/compile-errors`, `e2e/script-diagnostics.spec.ts`): the parser reads rustc's rendering (`error[E0425]`, `--> src/lib.rs:44:32`, caret lines). It is replaced by a reader of structured diagnostics (file, line, column, length, message, help), which the spike showed the build tool can produce from the assembler's reports. One error per build is the norm, and warnings need a choice (see Spike results).
- **Argument forms** (`lib/utils/procedure-inputs.ts`, 523 lines; `midenTypes`; `MidenTypeLayout`): they key on the manifest's layout as midenc writes it (`miden:base/core-types@1.0.0/felt`, `Struct` with fields, sizes in bytes) and on WIT parameter names. The MASM manifest keeps the layout's shape and changes the names (`AccountId`, `Asset` as bare struct names, `word` as an array of four felts), and carries no parameter names: see Spike results. The built-ins' hand-written signatures (`lib/types/default-scripts/*.ts`) copy midenc's layout and change with them.
- **Storage schema and note storage schema** (`PackageMetadata.storage`, `noteStorage`; the deploy form, `components/script/metadata-table.tsx`, the Simulate tab, `lib/simulation`, `storage-slot-name.tsx`, `storageSlotName` in `case.ts`): no source for either in a MASM package, and none is planned (decision 3): the schema-driven UI stays and is fed by hand-written schemas: the built-ins' as today, and new ones for the templates and the tutorial scripts. A script written from scratch, or imported, has none. The built-ins already work around this with hand-written schemas in `default-scripts/storage-schemas.ts`.
- **Built-in scripts** (`lib/types/default-scripts`): each carries a `rust` source (a Rust rendering of the standard component, shown in the editor) next to its `masm`. Drop the `rust` strings and show the MASM. `withDefaultScripts` already replaces persisted copies.
- **Embedded packages** (`lib/tutorials/basic-wallet.json` 803 lines, `basic-wallet.ts`, `counter-account.ts`, `count-reader.ts`, their three tests, `lib/simulation/embedded-packages.ts`): the Rust basic wallet exists only because a Rust note calls its account by the compiled package's roots. A MASM P2ID note calls the standard wallet, so it and its sync go. The counter and count-reader packages are re-embedded from MASM, or assembled on demand.
- **Tutorial code** (`lib/utils/tutorial-code.ts`, `components/tutorials/apply-code-button.tsx`): the Rust snippets the tutorials insert, anchored on template lines.
- **Create, import, share** (`create-script-dialog.tsx`, `import-project-dialog.tsx`, `lib/api.ts`, `scripts/share-project.mjs`, `docs/share-project.md`): the import dialog reads `src/lib.rs` and `miden-project.toml` from a folder; `share-project` is documented for `cargo-miden` users and posts `rust`.
- **Persisted state** (`lib/utils/state.ts`, `migrateScript`, saved projects, project links): scripts stored in browsers and in shared links hold `files["src/lib.rs"]` and a Rust-built `masp`. At the switch the API's Rust rows are deleted (decision 2) and a persisted state that holds a Rust script is reset whole on load (decision 13).
- **Analytics**: check `lib/analytics-events.ts` for a field that names a file or a language before renaming anything. Columns are positional, so a field is appended, never reused.

## What gets better

- Compile time: 2 to 3 s warm and 6 to 12 s after a sleep today, almost all cargo and cache layout. The assembly itself should be milliseconds; what remains is the network and the container's wake.
- No lockfile drift: the failure mode behind the 176 s production compiles, the weekly drift check and the "ship both repos together" rule all go.
- Standard wallets consume Playground notes. The embedded Rust wallet, its snapshot, `templates:sync` and the "stale snapshot leaves the note unconsumable and no e2e sees it" trap go.
- The API Worker bundle loses the examples' ~840 KiB of snapshots if examples compile on launch.
- api-compile's attack surface: no project code runs at build time.
- Reproducibility: `spec/masp-reproducibility.md` (rustc metadata, provenance patches) stops being a concern; an assembler is deterministic by construction.

## What gets worse or is lost

- Typed storage: Rust declared slots with names and types in the source. In MASM a slot is a name and a word, and the schema is given up, except where we write one by hand for our own content (decision 3).
- Note inputs as a typed record: same.
- Parameter names from WIT, including for types the forms don't know.
- The audience: tutorials 6 to 12 taught Rust contracts. MASM is a lower-level language to teach, and the tutorials need more explanation per line, not a translation.
- Nothing for verification of code deployed without a project: the spike assembled the counter with `CodeBuilder` (what the web SDK and the Rust client use) under two module paths, and with the project assembler under two namespaces, and every procedure root was the same. The namespace changes the export paths and so the package commitment, not the roots. So an account deployed from the SDK verifies against a `miden-project.toml` project of the same source, whatever namespace it names. One example only: code that uses `procref` or its own path could differ.

## Decisions

Taken with the user on 2026-11-24. "Recommended" marks where the choice follows this document's recommendation; the others replace it.

1. **The helper tools stay in Rust.** (Recommended.) "Remove Rust" means cargo-miden, midenc and Rust as a contract language. The MASM project assembler is a fourth helper tool, in Rust too.
2. **Existing Rust scripts in the Playground are deleted at the switch.** Not the recommendation, which was a read-only period first. When the Playground's MASM release ships (step 4), the API's Rust rows are deleted. Consequences: shared links and project links to a Rust script answer 404 from then on, and there is no legacy read-only view, banner or fork path to build. The user assumes no such link is in circulation (2026-11-26), so the switch doesn't check how shared, fork or project links to a deleted script behave. Deleting production rows is a destructive step: it runs once, on an explicit go-ahead, not as a side effect of a deploy.
3. **Schemas: none.** Chosen first as "ask upstream, ship without" (the recommendation); on 2026-11-24 the user set the working assumption that upstream plans no storage schema for MASM projects, so upstream isn't asked and shipping without is the design, not a stopgap. The deploy form takes raw slot names and words, and the Simulate tab works without a schema, as it does today for a package with null metadata. A note's storage is entered as raw felts. No convention of our own in `miden-project.toml`. The built-ins keep their hand-written schemas, and the templates and tutorial scripts get hand-written ones too (user, 2026-11-24; details below). What goes with it: `schemas.rs` and the `storage` / `noteStorage` keys in api-compile's answers, the registry's `schemas` column (stop writing, drop later, like `masm`), the viewer's storage listings, and nothing of the Playground's schema-driven UI (`metadata-table.tsx`, typed slot inputs, the note storage form): it stays, fed by hand-written schemas where there is one and absent where there is none. This is an assumption, not a fact read from upstream: if upstream ships a schema, this decision is reopened.
   Hand-written schemas for templates and tutorials (user, 2026-11-24):
   - **What**: each template with storage ships a schema next to its `.masm`, in the shape `metadata.storage` has today (slot name, `value` or `map`, types, default), as `default-scripts/storage-schemas.ts` does for the built-ins. The counter is the first case. The tutorials' embedded packages (`lib/tutorials/counter-account.ts`, `count-reader.ts`) carry theirs the same way.
   - **Where it attaches**: api-compile no longer returns a schema, so the Playground API sets `metadata` itself when it creates a package from a template or an example, instead of taking it from the compile answer. `compilePackage` must then stop overwriting `metadata.storage` with the (now empty) answer.
   - **Stale schemas** (user, 2026-11-24): a hand-written schema describes the template as shipped, and a user's edit can make it wrong. The rule: a script keeps its schema until the slot names in its source stop matching the schema's, and loses it then, falling back to the raw form. The check runs where `metadata` is written, on each compile: the slot names the source declares (its `word("…")` slot constants) against the schema's. `templates:check` fails when a template as shipped disagrees with its own schema, as it fails today on a stale snapshot. Not chosen: tutorial steps that carry the schema for their result.
   - **Notes: the schema goes on any edit of the source** (user, 2026-11-24). The slot-name rule works for account storage, where the source names each slot. A note's inputs have no names in MASM: the script reads them from memory by position (the P2ID note loads four items by pointer), so there is nothing to compare. For a note script the rule is therefore: it keeps its `noteStorage` schema while its source is byte for byte the template's as shipped, and loses it on the first edit, falling back to the raw form. A wrong form is worse than a raw one. Costs, accepted: a comment-only edit loses the typed form, and so does undoing an edit unless the source is back to the shipped bytes. Consequence for tutorial 8: after the step that adds `timelock_height` to the P2ID note, the note form is raw, so the step's copy tells the user which raw values to enter (step 5 rewrites it anyway). Not chosen: comparing what a note does declare (P2ID's `NUM_STORAGE_ITEMS`; not every note has one), and tutorial steps that carry the new schema.
   - **Note storage too** (confirmed by the user, 2026-11-24): the note templates get a hand-written `noteStorage` (the P2ID and counter note templates get a hand-written `noteStorage`), since the Simulate tab's note form reads it. The built-in notes have none today and stay that way.
   - **Not covered**: scripts a user writes from the blank templates, imports or forks from something schemaless, and everything in the verifier: its packages have no schema, and the viewer shows none.
4. **Parameter names: from the MASM source.** Settled by the spike: the manifest's signature has the parameters' types and no names (`params: [Felt]`), so the build tool reads the names from the source's AST. Not asked, since there was one sensible answer.
5. **Debug builds: one package with debug info.** (Recommended.) Confirmed by the spike: a dev and a release assembly have the same procedure roots, the same MAST forest commitment and the same `dependency_commitment`, which is the commitment api-compile reports. So the verified package is the dev one, `/compile-debug`, `debugCommitment`, `debugBuiltWith` and the `.debug.masp` route go, and Walnut's simulator downloads the one package: its contract changes, so its team is told before the change ships. To weigh when it is built: the dev counter is 396 KB against 1 KB, nearly all of it debug info, so a client that only deploys may want the release bytes.
6. **Existing verified records in the registry are deleted.** Not the recommendation, which was to keep them marked as Rust-built. When cargo leaves api-compile (step 6), the Rust-built packages, their verified accounts and notes and their stored `.masp` and `.debug.masp` files are deleted. Consequences: accounts and notes verified from Rust show as not verified, on Mainnet too, until someone verifies them again from MASM, which can only succeed for code that was redeployed from MASM; the viewer and the registry know only MASM afterwards; no discriminator column. This is a destructive step on the production database and bucket: it runs once, on an explicit go-ahead.
7. **The `masm` column: stop writing it at the switch, drop it later.** (Recommended.) The drop is its own migration in a later release. `Script.masm` stays for the built-ins.
8. **Built-ins are left as they are.** (Recommended.) They stay browser-assembled; only their `rust` source strings go, so the editor shows their MASM. Unifying them with user scripts is a possible follow-up, not part of this work.
9. **Miden Bank is hidden, not removed.** At the switch its card is hidden and its code stays, to be rewritten in MASM later (user, 2026-11-26; replaces "retired", the earlier recommendation). Nothing else is retired either: what can't work yet is hidden or marked unavailable. The Counter Contract example is rewritten in MASM.
10. **A script is one MASM file.** (Recommended.) One edited `.masm` file plus the generated `miden-project.toml`. Several modules can come later; the manifest format allows it.
11. **The Playground assembles on the server, through api-compile.** (Recommended.) Option A of [the architectural choice](#the-one-architectural-choice-where-the-playground-assembles). No browser assembly and no WASM assembler in this work.
12. **Rollout: both paths in api-compile, then drop cargo.** (Recommended.) api-compile builds MASM projects next to Rust ones, the Playground switches, cargo is removed last. No compile outage. Tutorials 6 to 12 are marked `unavailable` until each is rewritten.
13. **A persisted state that holds a Rust script is reset whole.** Not the recommendation, which was to drop the scripts and keep the rest. On load after the switch, a saved project or a tutorial state that contains a Rust script is discarded: its scripts, accounts, notes and transactions. Confirmed by the user on 2026-11-25: this covers the active workspace state as well as saved projects and resumable tutorials, so a workspace in which a Rust script is detected is removed whole. A state with no Rust script is untouched. The user is not told: no toast (user, 2026-11-25; not the recommendation, which was a one-time toast).

Still open:

- Decision 3 rests on an assumption about upstream (no storage schema planned). If it proves wrong, typed storage can come back.

## Spike results

Run on 2026-11-24 in the verifier repo, on the local branch `spike/masm-assembly` (directory `spike/masm-assembly`, nothing committed or pushed). A small Rust tool assembles a `miden-project.toml` project with `miden-assembly` 0.36.4 against the core, protocol, kernel and standards packages of the 0.18.0 crates. Three projects: a counter account component, a note that calls it, a transaction script that calls it.

Not done:

- **No deploy on a live network.** The plan was to deploy the counter on Testnet from the web SDK and run `miden-verifier` on it. What the spike changes in this document: decisions 4 and 5 are settled; the "unproven" worry about SDK-deployed code is gone for the simple case; `miden-verifier` needs no logic change; and api-compile can return structured diagnostics from the start, which makes the Playground's parser a JSON reader rather than a text parser.

## Order of work

The two repos deploy independently and the Playground depends on the verifier, so the verifier leads and never breaks the Playground in between.

1. **Spike**: done on 2026-11-24, see [Spike results](#spike-results). Left from it: one deploy on a live network once the helper tools are on the 0.18 crates (step 2).
2. **api-compile builds MASM projects, next to cargo.** A project without a `Cargo.toml` takes the new path; the answer's shape is unchanged where it can be. MASM examples and tests land here. The Playground keeps working on Rust.
3. **Registry, web-verifier, web-viewer accept and show MASM**, still showing Rust records until step 6.
4. **Playground API and editor on MASM**: files, manifests, templates, import, export, diagnostics, forms, the editor's language. This release is "the switch": the API's Rust rows are deleted (decision 2), persisted states that hold a Rust script are reset on load (decision 13), Miden Bank is retired (decision 9) and the `masm` column is no longer written (decision 7). Tutorials 6 to 12 and the Counter Contract example are marked `unavailable` for the gap, as tutorial 5 is today, rather than left broken.
5. **Playground content**: the Counter Contract example, then tutorials 6 to 12 one PR each, each with its e2e spec and a QA pass.
6. **api-compile drops cargo**: the toolchain, the cache, the isolation, the lockfile routes, the old tests. The registry refuses Rust, its Rust-built packages and records are deleted and the viewer's Rust rendering is removed (decision 6). New Testnet fixtures. This is the PR that shrinks the image.
7. **Cleanup in both repos**: docs, specs, drift workflow, dropped columns.
8. **`miden-verify`** is updated last (user, 2026-11-25), by us. Its plan is in that repo: `spec/remove-rust.md`. Consequence, accepted: from step 6 until the new CLI is released, the released CLI (0.7.0) uploads Rust projects and the registry refuses them. The CLI prints the registry's answer, so the registry's refusal at step 6 should say that Rust projects are no longer verified and name the CLI version to upgrade to.

Each step is cut into sub plans written for one agent in one session: this repo's are in [`remove-rust/`](remove-rust/README.md), the verifier's in `spec/remove-rust/` of its repo, and the CLI's is `spec/remove-rust.md` in `miden-verify`.

Steps 2 and 6 stay separate (decision 12): both paths live in api-compile for the duration of steps 3 to 5, and the Playground never loses compiling.
